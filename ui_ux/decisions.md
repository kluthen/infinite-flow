# UI/UX Decisions

- **D1 — Phrase-first landscape workspace.** The four measures occupy the primary canvas, with controls in a secondary rail or bottom sheet, so reading notation is never displaced by setup. No prior question.
- **D2 — Four measures remain together.** The first release presents all measures in one non-scrolling phrase strip; it never turns the result into a rolling staff. No prior question.
- **D3 — Conventional, transposition-aware engraving.** The notation renderer receives semantic events and uses a SMuFL music font, correct rhythmic values, rests, beams, barlines, ties, accidentals, time signature, clef, and chord symbols; noteheads are never positioned from raw screen coordinates. No prior question.
- **D4 — Theme architecture separates semantic from palette tokens.** Light and dark modes swap semantic color values without changing component classes, leaving room for future themes. No prior question.
- **D5 — Fade-only phrase replacement.** Regeneration crossfades rendered phrase content after successful generation, while the staff frame stays stable to preserve reading position. No prior question.
- **D6 — Full-width phrase-first workspace.** The score occupies the complete primary row and receives maximum available width for distant reading. Controls follow it as a vertically scrolling, reoriented section rather than taking a desktop side rail. No prior question.
- **D7 — Warm music-desk visual direction.** Retain the warm paper, graphite, and brass identity for light mode, with its dark ink counterpart for dark mode; revise the workspace hierarchy to make the score still more dominant. Closes Q1.
- **D8 — Landscape-only mobile and tablet experience.** The first-release workspace is supported in landscape orientation on mobile and tablet devices; desktop receives the full-width layout when width is sufficient. Closes Q3.
- **D9 — Pitch-class selection and spelling.** Every pitch class is selectable. Use sharp spellings by default, but use flat spellings when the selected key or mode convention requires them. The default tonal context is C Ionian. No prior question.
- **D10 — Confirmed initial presets.** The neutral preset uses static harmonic motion, quarter-note density, straight syncopation, sparse rests, arch contour, and middle register. The jazz preset uses eighth-note density, occasional offbeats, conversational space, wandering contour, and varying register. No prior question.
- **D11 — Arpeggio chaos levels.** `Predictable` traces chord tones in an orderly ascending or descending direction; `Varied` permits slight inversions and reordering; `Chaotic` permits the strongest reordering within the profile, contour, range, and resolution constraints. No prior question.
- **D12 — Display and theme defaults.** First load displays B-flat notation. The initial theme follows the operating-system preference, with a manual light/dark override available. No prior question.
- **D13 — Mode catalogue.** Every chromatic tonal center is selectable. The selectable collections are major, minor, and all seven church modes: Ionian, Dorian, Phrygian, Lydian, Mixolydian, Aeolian, and Locrian. Closes Q4.
- **D14 — C instrument profile.** The C profile represents a MIDI keyboard rather than a C-melody saxophone. Its playable generation range and register windows were subsequently settled by D17. Closes Q10.
- **D15 — C keyboard active range.** The first-release C/MIDI-keyboard profile uses concert MIDI 48 through 72 inclusive, corresponding to C3 through C5. Its register windows were subsequently settled by D17. No prior question.
- **D16 — Jazz preset harmonic motion.** Jazz applies gentle diatonic harmonic motion while retaining its diatonic harmonic plan; its bounded chromatic approaches and enclosures do not create altered harmony. Closes Q7.
- **D17 — Declarative profile range and window policies.** C MIDI keyboard uses 48-72 with Low 48-60, Middle 54-66, High 60-72; B-flat tenor uses 46-70 with Low 46-58, Middle 52-64, High 58-70; E-flat alto uses 51-75 with Low 51-63, Middle 57-69, High 63-75. `Varying` deterministically selects one feasible whole-phrase fixed window. Closes Q8.
- **D18 — Independent notation conventions.** Concert, B-flat tenor, and E-flat alto are display-only conventions rendered in treble G2 clef. Their written transforms are respectively unison, major ninth, and major sixth, and never change source events or generator policy. Closes Q9.
- **D19 — Profile-switch retain or regenerate.** Retain unchanged concert events only when they fit the new active range and current resolved whole-phrase register window; otherwise keep controls, select a fresh seed, and regenerate the complete phrase without transposing source events. Closes Q11.
- **D20 — Phone-landscape two-system fallback (signed off 2026-09-24).** Below `bp-tablet-landscape` (64rem), the score first attempts one staff system with all four measures; if that does not fit at the legibility floor, it is engraved as two staff systems of two measures each (bars 1-2 on the first system, bars 3-4 on the second) within the same staff area, with clef and key signature repeated on the second system and the 4/4 time signature shown only on the first. All four measure regions stay visibly equal in width in both layouts, and the two systems' measure columns stay aligned. At `bp-tablet-landscape` and above, the prior rule is unchanged: exactly one staff system or the notation-error state. If two systems also cannot fit at the legibility floor, the notation-error state applies. Notation is still never horizontally scrolled, clipped, split into more than two systems, or shrunk below the legibility floor, and the score's height still follows its content. See `screens/phrase-workspace/handoff.md` (Notation Contract, Responsive Behavior) and `screens/phrase-workspace/intent.md`. No prior question.

- **D24 — Character control group is static, not disclosable (signed off 2026-09-25).** It holds only Arpeggio chaos, is always visible, and is never collapsible or progressively disclosed — first release has no second character-level control that would justify hiding one behind an interaction. - **D25 — `control-summary` copy contract (signed off 2026-09-25).** `control-summary` is muted, small, static text in `control-section`, after `control-section-title` and `control-section-copy` and before `control-group-row`. It is plain text: never a live region, never announced, and carries no `aria-hidden` — it is not decorative, it is the only place a player reads tonal center, collection, and musical-profile state together, and plain static text that duplicates control state needs no ARIA suppression. It is independent of notation display mode, since the header already carries meter, tempo, and display mode. Copy shape: `{tonal center label} {collection label} · {musical profile or custom label} · {tension arc label} · {leapiness label}`, using a plain space between the tonal-center and collection labels and ` · ` (U+00B7 surrounded by spaces) between the remaining three segments. The tonal center label is the same label the tonal-center control shows (e.g. `C-sharp/D-flat`, per `src/components/controls/control-options.ts`). The musical-profile segment reads `Neutral` or `Jazz` when a preset is currently selected, or `Custom ({grammar} grammar)` during the custom state, where `{grammar}` is the same retained-grammar word `preset-status` already shows. It recomputes on every relevant control change, including during a custom edit. Examples: default load `C Ionian · Neutral · Lift · Shaped`; Jazz preset selected `C Ionian · Jazz · Lift · Shaped`; custom after a Neutral edit `C Ionian · Custom (Neutral grammar) · Lift · Shaped`; a C-sharp/D-flat Dorian selection at default `C-sharp/D-flat Dorian · Neutral · Lift · Shaped`. It keeps the existing `.control-summary` token (muted text, small size) already shared with `score-context`, `profile-range-summary`, and `tempo-readout`; no new token is needed. See `screens/phrase-workspace/handoff.md`. No prior question.
- **D26 — Unsupported rhythm combination documented in the phrase-workspace handoff (signed off 2026-09-25, from the `ux-critic` validation pass on Q5's `.inline-alert.alert-notice` variant).** The handoff previously never described the state this variant renders. See `screens/phrase-workspace/handoff.md` (Components and Content, States). The doc-side gap is closed; the code-side fix is tracked in `todo.md` and remains open on Q5 until applied and re-validated.
- **D27 — Profile switch clears the phrase when the new range invalidates it while rhythm is unsupported (signed off 2026-09-25).** This refines D19's regenerate branch for the one case D19 left unresolved: an instrument-profile switch whose unchanged concert phrase no longer fits the new active range and resolved whole-phrase register window, at a moment when the current rhythm-control combination is also unsupported. In that case the switch still applies — the new profile stays selected — but no regeneration is attempted; instead the prior phrase is cleared and the workspace returns to the empty state (`staff-frame staff-empty`, its instruction copy, and the `Generate phrase` label), while the unsupported-rhythm `inline-alert alert-notice` stays visible, still explaining why `Generate phrase` is blocked. No generation request runs. D19's existing regenerate branch is unchanged for the ordinary case: an invalid phrase when rhythm is supported still keeps controls, takes a fresh seed, and regenerates immediately. Also unchanged: a switch whose phrase still fits the new range keeps that phrase exactly as before, even while the rhythm combination is unsupported — validity against the new range, not rhythm support, decides whether the phrase is touched at all. See `screens/phrase-workspace/handoff.md` (Notation Contract, States). Closes Q6.
- **D28 — Read-only controls keep full color; a dashed ring signals "locked" (signed off 2026-09-25).** `.segmented-control.is-readonly` and `.field-group.is-readonly` (`ui_common.css`; the equivalent, but not byte-identical, rules exist in `src/styles/components.css`) previously set `opacity: 0.7`, which blends every label, selected-segment, and border color toward the card background and pushed some below WCAG AA. Computed at the current tokens: the light-theme field-label fell to 3.21:1, below the 4.5:1 text floor, once opacity blended `--color-text-muted` toward `--color-surface` (`#fffdf8`); dark-theme selected-segment text fell to 4.71:1, also under the floor, once blended toward `--color-surface` (`#23231f`) (the light-theme unselected-segment text/background pairing, by contrast, still passed at 5.05:1 blended -- the field-label and the dark selected-segment text were the actual failures). The fix removes the opacity rule entirely: read-only now renders every text, selected-segment, and border color exactly as the active state (contrast is therefore identical to the already-compliant baseline -- confirmed at full strength: light segment text 12.53:1, light selected-segment text 7.14:1, light field-label 6.24:1, light input-stepper text 16.01:1; dark segment text 11.69:1, dark selected-segment text 8.23:1, dark field-label 9.41:1, dark input-stepper text 13.88:1; all far above the 4.5:1 text floor) and instead marks the control "temporarily locked" with a new token, `--readonly-ring` (`0.125rem dashed var(--color-text-muted)`), applied as an `outline` with `outline-offset: var(--space-1)` plus the existing `pointer-events: none`. The ring itself meets the 3:1 non-text-UI-component floor as a meaningful state indicator: `--color-text-muted` against `--color-surface` computes to 6.24:1 in light and 9.41:1 in dark. `--color-border`, the file's other muted token, was rejected for the ring because it only reaches 2.16:1 against `--color-surface` in light theme (a separate, pre-existing default-border contrast gap this decision does not touch or fix -- logged for awareness only). Because every readonly field wraps its control in `field-group.is-readonly` and, for segmented fields, the nested `SegmentedControl` independently also receives `is-readonly` (`src/components/controls/FoundationControls.vue` and siblings pass `:readonly` to both), the ring is drawn once, on `field-group.is-readonly`, with `.field-group.is-readonly .segmented-control.is-readonly { outline: none; }` suppressing the inner control's own ring; the header's standalone notation-mode `segmented-control` (not wrapped in a `field-group`, and sitting on `--color-canvas` rather than `--color-surface`) keeps its own ring and still clears the 3:1 floor there (5.57:1 light, 10.63:1 dark). This session's task instructions explicitly excluded application source from its scope, so this decision applies the change only to `ui_common.css`, the frozen design-reference file per D21; `src/styles/theme.css` has no `--readonly-ring` equivalent yet and `src/styles/components.css` still carries the `opacity: 0.7` rule this decision replaces on both `is-readonly` selectors. D21 otherwise makes `theme.css`/`components.css` the canonical production source and ux-writer's to maintain directly -- this decision does not reassign that ownership, it defers the production edit to a follow-up ux-writer pass (tracked in `todo.md`) solely because this session was constrained not to touch `src/`. That follow-up is not a drop-in copy: production's spacing token is named `--spacing-1`, not `--space-1`, so the token must be adapted to production's naming when applied, not pasted verbatim. `mockups/phrase-workspace.html` renders only the ready state and needs no change. See `screens/phrase-workspace/handoff.md` (States, "Loading") and `ui_common.css`. No prior question.
- **D29 — Generation-failure alert shows one calm string per failure kind, never a raw code, a doubled prefix, or advice the player can't act on (signed off 2026-09-25).** The generation-failure `inline-alert alert-error` (a sibling of `score-toolbar`, not nested inside it -- see `screens/phrase-workspace/handoff.md`'s Layout Tree) had no defined copy; production concatenates a fixed `"Generation failed: "` prefix in `ScorePanel.vue` onto `state.generationError.message`, and `GenerationFailedError`'s own message (`workspace-session-result.ts`) is itself `"Generation failed: " + code`, so the rendered text doubles the prefix and exposes the raw `GenerationFailureCode` (e.g. `no_legal_pitch_plan`) to the player. This defines the banner's exact content instead, selected by failure kind and never assembled from a prefix plus the underlying error's own message: the six typed `GenerationFailureCode`s (`orchestration-types.ts`) each get a distinct, settings-grounded string naming the control group that code's own domain boundary consumes (harmony: tonal center/collection/harmonic motion/tension, and musical profile, per `module_harmony_candidate_domain.atom.md`'s full input list; rhythm: note density/syncopation/silence, echoing `UNSUPPORTED_RHYTHM_SETTING_MESSAGE`'s existing vocabulary for tone consistency; pitch: register/contour/rhythm, the broadest input surface per `specs/generative-process.md`). `no_eligible_register_window` names only a different contour, not a fixed register in place of Varying: with Varying the planner already searches all three register windows, each against its own full search budget (`specs/generative-process.md`), and this code is only reported once every window has been exhausted without hitting that budget (`generation-orchestrator.ts`), so a fixed Low/Middle/High request repeats the same exhausted search for that one window and fails again, as `no_legal_pitch_plan`, rather than succeeding -- suggesting it as a fix would be false advice. `search_limit_exceeded` is framed as a fixed, wall-clock-independent work budget being exhausted, not a timeout, per `docs/release/browser-and-offline-limits.md`'s "distinct from natural exhaustion" description (not `docs/generation-latency.md`, which does not contain that phrase); `result_validation_failed` explicitly does not blame the player's settings, since it is an implementation defect per the same doc. The string is replaced with: "This phrase search hit its work limit before finding a result. That doesn't prove this combination is impossible. Trying again may find a result, or try different settings." The other six strings are unchanged. Similarly, the claim that "None of the seven strings names a settings change as something the visible `Retry generation` action will apply on its own" and that clicking it "alone will not pick up a since-edited control until Q12 ... is resolved" is superseded: per D30, `Retry generation` builds its request from the current controls and profile with a fresh seed and identity, the same as `Regenerate phrase`, so the visible `Retry generation` button now does what four of the typed codes' strings promise -- the four that name specific settings (harmony, rhythm, pitch, register window) describe exactly what the button will pick up if the player edits the named control before pressing it. `search_limit_exceeded`'s string differs in kind: it names no specific setting, only a generic "try different settings" alongside "trying again" -- but the same mechanism applies, and its "trying again" half can succeed from the fresh seed alone with no control changed. The `generation-status` live-region announcement is unchanged (`Generation failed. Try again.`). See `screens/phrase-workspace/handoff.md` (Components and Content). No prior question. A related finding from writing this copy -- neither generation-error state (initial or with a prior valid score) had an in-app path back to a fresh attempt short of a page reload under the exact-replay retry semantics this decision originally assumed -- was logged as Q12 in `qna.md`; D30 resolves it by making `Retry generation` itself that fresh-attempt path. - **D30 — Retry generation builds a fresh request, not an exact replay (decided by the user, 2026-09-25).** After a failed generation, in both the "Initial generation error" and "Generation error" states, the `Retry generation` action now builds a new generation request from the current controls and selected instrument profile, with a fresh seed and request identity -- the same construction as `Regenerate phrase` -- rather than replaying `state.latestIntent` (the exact failed intent and seed) unchanged. This reverses the exact-replay retry semantics previously in force, which were described in `specs/generator-contract.md`'s "Session Ownership" section ("Retry generation repeats the exact failed intent; regenerate builds an intent from the current controls/profile and requests a fresh seed and identity") and were the premise of Q12 and of the D29 rationale passages amended above. Closes Q12. - **D31 — The generation-failure alert persists unchanged through control edits; only the next generation attempt updates it (2026-09-25).** D30 leaves one thing unstated: does `inline-alert alert-error` clear or update when the player edits a control after a failure, before pressing `Retry generation`? No live validation applies to it. Like `state.generationError` itself, the banner is a record of the last completed request's outcome, not a live-validated reflection of current control values -- consistent with every other control edit already leaving `generationError` untouched (only a generation attempt, or, per D27, a profile switch that clears the phrase, changes it). The banner's content and the `Retry generation` label stay exactly as shown until the next generation attempt starts: the banner leaves while that attempt runs (the workspace shows its ordinary in-flight state), success moves the workspace to Ready, and another failure brings the banner back with whatever failure kind that new attempt reports, per D29. This means a player can keep seeing a harmony/rhythm/pitch/register-window hint that names a control they have since changed, while they finish adjusting other controls before pressing `Retry generation` -- intentional, not a bug: the hint described the failed request, and re-validating it live against every keystroke would mean running the generator outside an explicit request, which this workspace never does. See `screens/phrase-workspace/handoff.md` (States, "Initial generation error" and "Generation error"). No prior question.
- **D32 — A generation-failure banner and a co-active notation error are reachable together; the header exposes `Retry notation`, and the banner stays passively visible until it resolves (signed off 2026-09-25).** Follow-up from the Step 10 release review: no state previously described a generation-error banner coexisting with the `Retry notation` label (`WorkspaceHeader.vue:40-41`). Traced against `WorkspaceHeader.vue`, `ScorePanel.vue`, `use-generation-session.ts`, `generation-session-profile-switch.ts`, and `use-notation-coordinator.ts`:
  - **The combined state is reachable, in one order only, and by three distinct paths.** `run()` (backing `generate`, `regenerate`, `retryGeneration`, and the profile-switch regenerate branch) clears `generationError`, `notationError`, and `failedNotationMode` together the instant it starts, before generation itself runs. So a notation error already showing can never survive *as a live-reported state* into a later generation failure -- starting any new generation attempt always clears the flag first, and if that attempt then fails, only `generationError` ends up set again. (A related but distinct gap -- clearing the flag this way does not always repair what the flag was describing, since the earlier notation failure already blanked the staff and this new failure never asks for a redraw -- is documented separately below and is not decided in this entry; see "Two pre-existing gaps surfaced while tracing this decision" below.) The only order that reaches the combined state at all is the reverse: a generation attempt fails while a prior valid score is retained (`state.result` is untouched by the catch branch in `run()`; `generationError` is set; `notationError` stays null -- this is the existing **Generation error** state), and only afterward does a redraw of that retained score fail through one of three paths, none of which check or touch `generationError`: (1) an unsolicited out-of-band redraw -- a viewport resize or breakpoint crossing routed through `PhraseScore`'s own `@notation-error` emit, `use-notation-coordinator.ts`'s `handleNotationError`, and `reportNotationFailure`, which requires exactly `state.operation === 'idle' && state.result !== null`; (2) an ordinary display-mode switch, `setNotationMode` calling `runNotation` when `state.result !== null` (`use-generation-session.ts:209-215`) -- the header's notation-mode `segmented-control` is read-only only while an operation is running (`WorkspaceHeader.vue`'s `operationRunning`), so it is usable during the idle **Generation error** state; or (3) an instrument-profile switch whose retain branch calls `redrawNotation` (`generation-session-profile-switch.ts:86-88`, itself `runNotation`), also usable while idle in **Generation error**. All three set `notationError` on top of the still-set `generationError`. This can only happen from **Generation error** (a prior score retained), never from **Initial generation error** (`state.result === null`, so there is no mounted phrase for a redraw to fail against, and none of the three paths above can run: `reportNotationFailure`'s guard rejects it, and `setNotationMode`/`selectInstrumentProfile`'s redraw branches both require a result).
  - **What is visible.** The generation-failure banner (`ScorePanel.vue`'s `inline-alert alert-error`, a sibling of `score-toolbar` inside `score-panel`, rendered above `staff-viewport` -- see `screens/phrase-workspace/handoff.md`'s Layout Tree) is gated only on `state.generationError !== null`; it does not check `notationError` and so stays visible unchanged. `staff-frame` simultaneously switches to `staff-error` (`notationError` outranks `result` in `staffFrameStateClass`), showing "Notation error: {message}" in place of the score: `PhraseScore.vue` clears both its staging and visible SVG content (`replaceChildren()`) before emitting the failure, so the staff area is blank, not showing the retained phrase underneath -- consistent with the existing **Notation error** state's "replaces only the affected score content with an error message," not a new behavior. `PhraseScore` stays mounted (so a later `Retry notation` redraws into the same instance) but presents nothing. Both banners are on screen together: the generation-failure banner above the staff viewport, the blank-staff notation-error panel inside it.

None of these redraws is guaranteed to reproduce the phrase exactly as it last looked, either: a resize or breakpoint crossing redraws in whatever display mode the last attempt used; a display-mode pick redraws in the newly selected mode; a retaining profile switch redraws in the mode the header's control already shows (`state.presentation.notationMode`), unchanged -- and per D35 (implementation pending -- see `todo.md`), an out-of-band recovery also reports and commits that mode into `presentation.notationMode`, so the header's control does not disagree with what is actually shown once any of these redraws succeeds and that implementation lands. So this is not a dead end: some path out always exists, and D34 additionally ensures the screen never misrepresents the blank staff as ready while a player looks for one. It also is not specific to this combined state -- the same regenerate-branch failure reachable from the standalone **Notation error** state (no generation-failure banner involved at all) resolves identically once D34 is implemented. Closes Q14; see D34. A profile switch whose phrase still fits the new range never reaches this check at all and redraws or retains the phrase regardless of rhythm support, per the Notation Contract.

- **D35 — An out-of-band notation recovery or failure now reports the mode the notation coordinator actually rendered, not a value derived from committed or previously-failed session state (user decision, 2026-09-25; no prior question).** Flagged directly to `coding-leader` during this session's D32 validation rather than routed through `qna.md`, since it is a pre-existing implementation defect rather than an open design question: `reportNotationRecovered` (`use-generation-session.ts`) -- the success counterpart to `reportNotationFailure` that `use-notation-coordinator.ts`'s `handleEngraved`/`handleNotationError` route an out-of-band redraw result to whenever no `notate()` promise is pending -- cleared `notationError`/`failedNotationMode` without committing `presentation.notationMode`, unlike `runNotation`'s own success branch, which does commit it.
