# UI/UX Decisions

- **D1 — Phrase-first landscape workspace.** The four measures occupy the primary canvas, with controls in a secondary rail or bottom sheet, so reading notation is never displaced by setup. No prior question.
- **D2 — Four measures remain together.** The first release presents all measures in one non-scrolling phrase strip; it never turns the result into a rolling staff. No prior question.
- **D3 — Conventional, transposition-aware engraving.** The notation renderer receives semantic events and uses a SMuFL music font, correct rhythmic values, rests, beams, barlines, ties, accidentals, time signature, clef, and chord symbols; noteheads are never positioned from raw screen coordinates. No prior question.
- **D4 — Theme architecture separates semantic from palette tokens.** Light and dark modes swap semantic color values without changing component classes, leaving room for future themes. No prior question.
- **D5 — Fade-only phrase replacement.** Regeneration crossfades rendered phrase content after successful generation, while the staff frame stays stable to preserve reading position. No prior question.
- **D6 — Full-width phrase-first workspace.** The score occupies the complete primary row and receives maximum available width for distant reading. Controls follow it as a vertically scrolling, reoriented section rather than taking a desktop side rail. No prior question.
- **D7 — Warm music-desk visual direction.** Retain the warm paper, graphite, and brass identity for light mode, with its dark ink counterpart for dark mode; revise the workspace hierarchy to make the score still more dominant. Closes Q1.
- **D8 — Landscape-only mobile and tablet experience.** The first-release workspace is supported in landscape orientation on mobile and tablet devices; desktop receives the full-width layout when width is sufficient. Closes Q3.
- **D9 — Pitch-class selection and spelling.** Every pitch class is selectable. Use sharp spellings by default, but use flat spellings when the selected key or mode convention requires them. The default tonal context is C Ionian. No prior question.
- **D10 — Confirmed initial presets.** The neutral preset uses static harmonic motion, quarter-note density, straight syncopation, sparse rests, arch contour, and middle register. The jazz preset uses eighth-note density, occasional offbeats, conversational space, wandering contour, and varying register. No prior question.
- **D11 — Arpeggio chaos levels.** `Predictable` traces chord tones in an orderly ascending or descending direction; `Varied` permits slight inversions and reordering; `Chaotic` permits the strongest reordering within the profile, contour, range, and resolution constraints. No prior question.
- **D12 — Display and theme defaults.** First load displays B-flat notation. The initial theme follows the operating-system preference, with a manual light/dark override available. No prior question.
- **D13 — Mode catalogue.** Every chromatic tonal center is selectable. The selectable collections are major, minor, and all seven church modes: Ionian, Dorian, Phrygian, Lydian, Mixolydian, Aeolian, and Locrian. Closes Q4.
- **D14 — C instrument profile.** The C profile represents a MIDI keyboard rather than a C-melody saxophone. Its playable generation range and register windows were subsequently settled by D17. Closes Q10.
- **D15 — C keyboard active range.** The first-release C/MIDI-keyboard profile uses concert MIDI 48 through 72 inclusive, corresponding to C3 through C5. Its register windows were subsequently settled by D17. No prior question.
- **D16 — Jazz preset harmonic motion.** Jazz applies gentle diatonic harmonic motion while retaining its diatonic harmonic plan; its bounded chromatic approaches and enclosures do not create altered harmony. Closes Q7.
- **D17 — Declarative profile range and window policies.** C MIDI keyboard uses 48-72 with Low 48-60, Middle 54-66, High 60-72; B-flat tenor uses 46-70 with Low 46-58, Middle 52-64, High 58-70; E-flat alto uses 51-75 with Low 51-63, Middle 57-69, High 63-75. `Varying` deterministically selects one feasible whole-phrase fixed window. Closes Q8.
- **D18 — Independent notation conventions.** Concert, B-flat tenor, and E-flat alto are display-only conventions rendered in treble G2 clef. Their written transforms are respectively unison, major ninth, and major sixth, and never change source events or generator policy. Closes Q9.
- **D19 — Profile-switch retain or regenerate.** Retain unchanged concert events only when they fit the new active range and current resolved whole-phrase register window; otherwise keep controls, select a fresh seed, and regenerate the complete phrase without transposing source events. Closes Q11.
- **D20 — Phone-landscape two-system fallback (signed off 2026-09-24).** Below `bp-tablet-landscape` (64rem), the score first attempts one staff system with all four measures; if that does not fit at the legibility floor, it is engraved as two staff systems of two measures each (bars 1-2 on the first system, bars 3-4 on the second) within the same staff area, with clef and key signature repeated on the second system and the 4/4 time signature shown only on the first. All four measure regions stay visibly equal in width in both layouts, and the two systems' measure columns stay aligned. At `bp-tablet-landscape` and above, the prior rule is unchanged: exactly one staff system or the notation-error state. If two systems also cannot fit at the legibility floor, the notation-error state applies. Notation is still never horizontally scrolled, clipped, split into more than two systems, or shrunk below the legibility floor, and the score's height still follows its content. See `screens/phrase-workspace/handoff.md` (Notation Contract, Responsive Behavior) and `screens/phrase-workspace/intent.md`. No prior question.
- **D21 — Production Tailwind token/component source (Step 9).** `src/styles/theme.css` and `src/styles/components.css` (imported via `src/styles/index.css`) are now the canonical, ux-writer-owned production token and component-class source, superseding `ui_common.css` for the application. `ui_common.css` is retained, frozen, as a design reference for `mockups/phrase-workspace.html` only, and is marked as such at its top. The production pass added `.segment` min-inline-size 2.75rem, `.stepper-button`, the `.input-stepper` group, staff-colour overrides for VexFlow SVG fill/stroke/text, and a new `.inline-alert.alert-notice` calm-notice variant for the unsupported-rhythm message; it omitted review-shell, score-caption, score-subtitle, score-art, the illustration classes, and control-sheet as mockup-only. See `index.md` ("How future UI changes flow"). No prior question. The `.inline-alert.alert-notice` variant specifically is pending `ux-critic` validation — see Q5.
- **D22 — Custom musical-preset state keeps no checked radio (signed off 2026-09-25).** After a manual edit to any preset-controlled field, the Neutral/Jazz musical-profile-preset `segmented-control` shows no checked option. This is the sole sanctioned exception to "exactly one segment is checked when a value is active" in this design set. ARIA permits a `radiogroup` with no checked radio, and adding an unselectable third "Custom" radio would misrepresent Custom as a selectable preset when it is not — it is the absence of a preset. The first option (`Neutral`) becomes the roving tab stop when no option is checked, and `preset-status is-custom` states which grammar (`Neutral` or `Jazz`) is retained. This confirms and formalizes behavior the handoff already described; the master spec will be amended separately to record the exception. See `screens/phrase-workspace/handoff.md` (Components and Content). No prior question.
- **D23 — Contour option order is Rising, Falling, Arch, Wandering (signed off 2026-09-25).** This matches the master spec and the `CONTOURS` domain catalog (`src/domain/controls/generation-controls.ts`). `mockups/phrase-workspace.html` previously showed Rising, Arch, Wandering, Falling; corrected to match. No prior question.
- **D24 — Character control group is static, not disclosable (signed off 2026-09-25).** It holds only Arpeggio chaos, is always visible, and is never collapsible or progressively disclosed — first release has no second character-level control that would justify hiding one behind an interaction. The wrapper element is renamed from `character-disclosure` to `character-static` throughout this design set (handoff, mockup, `ui_common.css`) to stop implying a disclosure widget. The production class in `src/styles/components.css` and the wrapper in `CharacterControls.vue` are renamed to match by a coding agent. See `screens/phrase-workspace/handoff.md`. No prior question.
- **D25 — `control-summary` copy contract (signed off 2026-09-25).** `control-summary` is muted, small, static text in `control-section`, after `control-section-title` and `control-section-copy` and before `control-group-row`. It is plain text: never a live region, never announced, and carries no `aria-hidden` — it is not decorative, it is the only place a player reads tonal center, collection, and musical-profile state together, and plain static text that duplicates control state needs no ARIA suppression. It is independent of notation display mode, since the header already carries meter, tempo, and display mode. Copy shape: `{tonal center label} {collection label} · {musical profile or custom label} · {tension arc label} · {leapiness label}`, using a plain space between the tonal-center and collection labels and ` · ` (U+00B7 surrounded by spaces) between the remaining three segments. The tonal center label is the same label the tonal-center control shows (e.g. `C-sharp/D-flat`, per `src/components/controls/control-options.ts`). The musical-profile segment reads `Neutral` or `Jazz` when a preset is currently selected, or `Custom ({grammar} grammar)` during the custom state, where `{grammar}` is the same retained-grammar word `preset-status` already shows. It recomputes on every relevant control change, including during a custom edit. Examples: default load `C Ionian · Neutral · Lift · Shaped`; Jazz preset selected `C Ionian · Jazz · Lift · Shaped`; custom after a Neutral edit `C Ionian · Custom (Neutral grammar) · Lift · Shaped`; a C-sharp/D-flat Dorian selection at default `C-sharp/D-flat Dorian · Neutral · Lift · Shaped`. It keeps the existing `.control-summary` token (muted text, small size) already shared with `score-context`, `profile-range-summary`, and `tempo-readout`; no new token is needed. See `screens/phrase-workspace/handoff.md`. No prior question.
- **D26 — Unsupported rhythm combination documented in the phrase-workspace handoff (signed off 2026-09-25, from the `ux-critic` validation pass on Q5's `.inline-alert.alert-notice` variant).** The handoff previously never described the state this variant renders. It now defines the rhythm `control-group`'s `inline-alert alert-notice` as a persistent, always-in-the-accessibility-tree `role="status"` live region reporting an unsupported note-density/syncopation/silence-density combination and a nearer-supported-combination suggestion, and adds a companion "Unsupported rhythm combination" state: every phrase action except `Retry notation` is disabled while blocked, and every control, including rhythm, stays editable. This documents behavior the domain already implements (`rule_unsupported_rhythm_settings_block_generation`); it settles no new product rule. The same validation pass found the region is currently rendered with `v-show` in `src/components/controls/RhythmControls.vue`, which removes it from the accessibility tree while empty and defeats the persistent-region intent this handoff and that component's own comment both describe; a coding agent must keep the `role="status"` element always mounted and toggle only its visible `inline-alert alert-notice` styling and content. See `screens/phrase-workspace/handoff.md` (Components and Content, States). The doc-side gap is closed; the code-side fix is tracked in `todo.md` and remains open on Q5 until applied and re-validated.
- **D27 — Profile switch clears the phrase when the new range invalidates it while rhythm is unsupported (signed off 2026-09-25).** This refines D19's regenerate branch for the one case D19 left unresolved: an instrument-profile switch whose unchanged concert phrase no longer fits the new active range and resolved whole-phrase register window, at a moment when the current rhythm-control combination is also unsupported. In that case the switch still applies — the new profile stays selected — but no regeneration is attempted; instead the prior phrase is cleared and the workspace returns to the empty state (`staff-frame staff-empty`, its instruction copy, and the `Generate phrase` label), while the unsupported-rhythm `inline-alert alert-notice` stays visible, still explaining why `Generate phrase` is blocked. No generation request runs. D19's existing regenerate branch is unchanged for the ordinary case: an invalid phrase when rhythm is supported still keeps controls, takes a fresh seed, and regenerates immediately. Also unchanged: a switch whose phrase still fits the new range keeps that phrase exactly as before, even while the rhythm combination is unsupported — validity against the new range, not rhythm support, decides whether the phrase is touched at all. See `screens/phrase-workspace/handoff.md` (Notation Contract, States). Closes Q6.
- **D28 — Read-only controls keep full color; a dashed ring signals "locked" (signed off 2026-09-25).** `.segmented-control.is-readonly` and `.field-group.is-readonly` (`ui_common.css`; the equivalent, but not byte-identical, rules exist in `src/styles/components.css`) previously set `opacity: 0.7`, which blends every label, selected-segment, and border color toward the card background and pushed some below WCAG AA. Computed at the current tokens: the light-theme field-label fell to 3.21:1, below the 4.5:1 text floor, once opacity blended `--color-text-muted` toward `--color-surface` (`#fffdf8`); dark-theme selected-segment text fell to 4.71:1, also under the floor, once blended toward `--color-surface` (`#23231f`) (the light-theme unselected-segment text/background pairing, by contrast, still passed at 5.05:1 blended -- the field-label and the dark selected-segment text were the actual failures). The fix removes the opacity rule entirely: read-only now renders every text, selected-segment, and border color exactly as the active state (contrast is therefore identical to the already-compliant baseline -- confirmed at full strength: light segment text 12.53:1, light selected-segment text 7.14:1, light field-label 6.24:1, light input-stepper text 16.01:1; dark segment text 11.69:1, dark selected-segment text 8.23:1, dark field-label 9.41:1, dark input-stepper text 13.88:1; all far above the 4.5:1 text floor) and instead marks the control "temporarily locked" with a new token, `--readonly-ring` (`0.125rem dashed var(--color-text-muted)`), applied as an `outline` with `outline-offset: var(--space-1)` plus the existing `pointer-events: none`. The ring itself meets the 3:1 non-text-UI-component floor as a meaningful state indicator: `--color-text-muted` against `--color-surface` computes to 6.24:1 in light and 9.41:1 in dark. `--color-border`, the file's other muted token, was rejected for the ring because it only reaches 2.16:1 against `--color-surface` in light theme (a separate, pre-existing default-border contrast gap this decision does not touch or fix -- logged for awareness only). Because every readonly field wraps its control in `field-group.is-readonly` and, for segmented fields, the nested `SegmentedControl` independently also receives `is-readonly` (`src/components/controls/FoundationControls.vue` and siblings pass `:readonly` to both), the ring is drawn once, on `field-group.is-readonly`, with `.field-group.is-readonly .segmented-control.is-readonly { outline: none; }` suppressing the inner control's own ring; the header's standalone notation-mode `segmented-control` (not wrapped in a `field-group`, and sitting on `--color-canvas` rather than `--color-surface`) keeps its own ring and still clears the 3:1 floor there (5.57:1 light, 10.63:1 dark). This session's task instructions explicitly excluded application source from its scope, so this decision applies the change only to `ui_common.css`, the frozen design-reference file per D21; `src/styles/theme.css` has no `--readonly-ring` equivalent yet and `src/styles/components.css` still carries the `opacity: 0.7` rule this decision replaces on both `is-readonly` selectors. D21 otherwise makes `theme.css`/`components.css` the canonical production source and ux-writer's to maintain directly -- this decision does not reassign that ownership, it defers the production edit to a follow-up ux-writer pass (tracked in `todo.md`) solely because this session was constrained not to touch `src/`. That follow-up is not a drop-in copy: production's spacing token is named `--spacing-1`, not `--space-1`, so the token must be adapted to production's naming when applied, not pasted verbatim. `mockups/phrase-workspace.html` renders only the ready state and needs no change. See `screens/phrase-workspace/handoff.md` (States, "Loading") and `ui_common.css`. No prior question.
- **D29 — Generation-failure alert shows one calm string per failure kind, never a raw code, a doubled prefix, or advice the player can't act on (signed off 2026-09-25).** `score-toolbar`'s `inline-alert alert-error` had no defined copy; production concatenates a fixed `"Generation failed: "` prefix in `ScorePanel.vue` onto `state.generationError.message`, and `GenerationFailedError`'s own message (`workspace-session-result.ts`) is itself `"Generation failed: " + code`, so the rendered text doubles the prefix and exposes the raw `GenerationFailureCode` (e.g. `no_legal_pitch_plan`) to the player. This defines the banner's exact content instead, selected by failure kind and never assembled from a prefix plus the underlying error's own message: the six typed `GenerationFailureCode`s (`orchestration-types.ts`) each get a distinct, settings-grounded string naming the control group that code's own domain boundary consumes (harmony: tonal center/collection/harmonic motion/tension, and musical profile, per `module_harmony_candidate_domain.atom.md`'s full input list; rhythm: note density/syncopation/silence, echoing `UNSUPPORTED_RHYTHM_SETTING_MESSAGE`'s existing vocabulary for tone consistency; pitch: register/contour/rhythm, the broadest input surface per `specs/generative-process.md`). `no_eligible_register_window` names only a different contour, not a fixed register in place of Varying: with Varying the planner already searches all three register windows, each against its own full search budget (`specs/generative-process.md`), and this code is only reported once every window has been exhausted without hitting that budget (`generation-orchestrator.ts`), so a fixed Low/Middle/High request repeats the same exhausted search for that one window and fails again, as `no_legal_pitch_plan`, rather than succeeding -- suggesting it as a fix would be false advice. `search_limit_exceeded` is framed as a fixed, wall-clock-independent work budget being exhausted, not a timeout, per `docs/release/browser-and-offline-limits.md`'s "distinct from natural exhaustion" description (not `docs/generation-latency.md`, which does not contain that phrase); `result_validation_failed` explicitly does not blame the player's settings, since it is an implementation defect per the same doc. Every other failure -- a `GenerationWorkerCrashError`, a `GenerationWorkerTransportError` (`generation-worker-client.ts`), or any other unrecognized `Error` -- shows one shared generic string. **Amended by D30 (2026-09-25):** the `search_limit_exceeded` string and this paragraph's framing of `Retry generation` originally assumed exact-replay retry semantics that D30 below reverses. The `search_limit_exceeded` string previously read "This phrase search hit its work limit before finding a result. That doesn't prove this combination is impossible, and repeating the identical request won't change the outcome." -- stated on the premise that `Retry generation` replays the identical request and would hit the identical budget again. That premise no longer holds: per D30, `Retry generation` now builds a fresh request with a new seed, so a retry explores a different search path and is not guaranteed to hit the same budget. The string is replaced with: "This phrase search hit its work limit before finding a result. That doesn't prove this combination is impossible. Trying again may find a result, or try different settings." The other six strings are unchanged. Similarly, the claim that "None of the seven strings names a settings change as something the visible `Retry generation` action will apply on its own" and that clicking it "alone will not pick up a since-edited control until Q12 ... is resolved" is superseded: per D30, `Retry generation` builds its request from the current controls and profile with a fresh seed and identity, the same as `Regenerate phrase`, so the visible `Retry generation` button now does what four of the typed codes' strings promise -- the four that name specific settings (harmony, rhythm, pitch, register window) describe exactly what the button will pick up if the player edits the named control before pressing it. `search_limit_exceeded`'s string differs in kind: it names no specific setting, only a generic "try different settings" alongside "trying again" -- but the same mechanism applies, and its "trying again" half can succeed from the fresh seed alone with no control changed. The `generation-status` live-region announcement is unchanged (`Generation failed. Try again.`). See `screens/phrase-workspace/handoff.md` (Components and Content). No prior question. A related finding from writing this copy -- neither generation-error state (initial or with a prior valid score) had an in-app path back to a fresh attempt short of a page reload under the exact-replay retry semantics this decision originally assumed -- was logged as Q12 in `qna.md`; D30 resolves it by making `Retry generation` itself that fresh-attempt path. (This finding was originally mislabeled Q7 in an earlier draft of this entry; Q7 was already spent by D16 on an unrelated jazz-harmonic-motion question. Corrected to Q12, the next unused ID, during D30's validation pass.)
- **D30 — Retry generation builds a fresh request, not an exact replay (decided by the user, 2026-09-25).** After a failed generation, in both the "Initial generation error" and "Generation error" states, the `Retry generation` action now builds a new generation request from the current controls and selected instrument profile, with a fresh seed and request identity -- the same construction as `Regenerate phrase` -- rather than replaying `state.latestIntent` (the exact failed intent and seed) unchanged. This reverses the exact-replay retry semantics previously in force, which were described in `specs/generator-contract.md`'s "Session Ownership" section ("Retry generation repeats the exact failed intent; regenerate builds an intent from the current controls/profile and requests a fresh seed and identity") and were the premise of Q12 and of the D29 rationale passages amended above. Reason: under exact replay, a deterministic failure (any of the six typed `GenerationFailureCode`s -- `no_legal_harmony_plan`, `no_legal_rhythm_plan`, `no_legal_pitch_plan`, `no_eligible_register_window`, `search_limit_exceeded`, `result_validation_failed`) could never succeed by pressing `Retry generation` alone, and editing a control afterward neither cleared the alert nor changed what the button would do, leaving no in-app path back to a fresh attempt short of a page reload (or, narrowly, a profile switch that happens to invalidate the phrase per D27). Closes Q12. Only the action's request construction changes -- what the button says and where it sits is untouched.

- **D31 — The generation-failure alert persists unchanged through control edits; only the next generation attempt updates it (2026-09-25).** D30 leaves one thing unstated: does `inline-alert alert-error` clear or update when the player edits a control after a failure, before pressing `Retry generation`? No live validation applies to it. Like `state.generationError` itself, the banner is a record of the last completed request's outcome, not a live-validated reflection of current control values -- consistent with every other control edit already leaving `generationError` untouched (only a generation attempt, or, per D27, a profile switch that clears the phrase, changes it). The banner's content and the `Retry generation` label stay exactly as shown until the next generation attempt starts: the banner leaves while that attempt runs (the workspace shows its ordinary in-flight state), success moves the workspace to Ready, and another failure brings the banner back with whatever failure kind that new attempt reports, per D29. This means a player can keep seeing a harmony/rhythm/pitch/register-window hint that names a control they have since changed, while they finish adjusting other controls before pressing `Retry generation` -- intentional, not a bug: the hint described the failed request, and re-validating it live against every keystroke would mean running the generator outside an explicit request, which this workspace never does. See `screens/phrase-workspace/handoff.md` (States, "Initial generation error" and "Generation error"). No prior question.
