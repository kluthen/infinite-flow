# Phrase Workspace Intent

The score is deliberately the focal point. A player should be able to sight-read the phrase without searching for where bar three begins or which chord governs a note. Four visibly equal measure regions, strong barlines, and chord symbols placed above their harmonic entry give the phrase its form at a glance. At `bp-tablet-landscape` and above, that takes the form of one unbroken staff system holding all four measures. On phone landscape, below `bp-tablet-landscape`, the same legibility floor that keeps the score readable at a distance can make one system too small to hold all four bars; rather than shrink the score past that floor, the workspace falls back to two aligned staff systems of two measures each, so the phrase still reads as one four-bar form split at a natural halfway point rather than as compressed or illegible notation.

The header gives only essential reading context: controller connection status, meter, tempo, and the whole-phrase action. There is no separate notation-display control to place there — the score always renders in the currently selected instrument profile's own written pitch. It omits generator internals, seed data, and a performance interpretation because these do not help a player read the proposal. `control-summary`, a single muted line after the control section's title and intro copy but before its control groups, restates written key, collection, musical profile (or the custom state), tension, and leapiness as one compact settings line so a player scrolling into controls does not have to re-scan every field-group to know what they are about to change; it is static text, not a live region, since it only mirrors state the controls already show. Instrument profile and its active range stay with the instrument-profile control itself, in `profile-range-summary`, because that information is explanatory metadata for one specific choice rather than a top-level setting a player needs restated at a glance.

The score fills the first content row on every landscape target. Controls follow it in the vertical reading order, so a player can read the staff from a distance before scrolling to shape a replacement. Wide displays orient control groups horizontally across the page; landscape phones stack them into a compact scrollable section. The character group is static rather than disclosed: it holds only Arpeggio chaos, first release has no second character-level control, and hiding a group's only control behind a toggle would add friction without protecting the player from anything.

`controller-status` occupies the header rather than a persistent workspace panel because connecting a controller is occasional, not continuous, attention (checked once at the start of a practice sitting, revisited only rarely) and because a persistent panel would claim width from the score, the one region this screen never yields to UI chrome. It is deliberately understated until a controller has actually connected — a plain `btn`, not `btn-primary`, since connecting a controller supports the practice loop rather than being the practice loop itself — and becomes a quiet status badge once one has, or an error-toned "MIDI access blocked" badge if the browser refuses permission, the one state outside a session the player cannot fix from inside the app. Once a controller has connected, the header never falls back to the `Connect controller` button for the rest of the page session: the player already knows what it does. Every badge carries words as well as its coloured dot. Every badge form is also the same width: the label area is sized once for the longest fixed label, "Controller disconnected", and a longer device name is cut with an ellipsis (its full name shows on hover and in the sheet). A badge that changes its words — a device name, "No controller", "MIDI access blocked", "Controller disconnected" — therefore never nudges the meter, tempo, theme control or phrase action beside it, at any screen size; a header that twitches while the player reads is exactly the kind of movement this screen refuses the score. A controller unplugged between sessions is not a fault: the badge quietly reads "No controller", and the same device plugged back in simply reattaches and the badge returns, with no sheet and no new check. Between sessions it opens the connection sheet (`flows/controller-connection/`, `screens/controller-connection/`); during a session it is a status display only, because connecting, switching device, and re-running the check all happen between sessions. It stays in place during a session — disabled if it is the `Connect controller` button — so the header never shifts. Falling silent changes nothing on this screen: the phrase keeps rolling and unplayed notes simply stay unlit. A controller that is actually unplugged mid-session is different and deliberately loud: the player would otherwise keep playing into silence and conclude the app stopped listening. So an error-toned banner with a live countdown appears above the staff, in space the session keeps free for it so the staff never moves, and the header badge takes the same tone. The banner's sentence and its countdown read as one line of ordinary text, so the countdown sits inside the sentence rather than in a column of its own. The banner goes the moment the same controller is plugged back in, and if the countdown runs out the session ends exactly as a silence timeout ends it. No sheet ever opens over a running session: it would hide Stop and the staff at the moment the player needs them. See `flows/controller-connection/intent.md` for the full reasoning.

The header takes only the space necessary for brand, controller status, meter and tempo, theme override, and the whole-phrase action. The screen must not shrink notation to accommodate UI chrome. When available space is constrained, control content moves below the score before the score uses a smaller engraving scale. The defined landscape targets are a product constraint; portrait mobile and tablet views receive a rotate-device message instead of an illegible rearrangement, while desktop remains usable when it has sufficient width. A profile switch never carries a phrase forward: with a phrase shown, it always regenerates a complete replacement in the new profile's written pitch, with a fresh seed, rather than testing whether the old phrase would still fit. The UI makes that regenerated replacement clear through the normal stable-frame loading and fade sequence rather than presenting a silent pitch transposition.
