# Open Questions

- **Q15 — while a notation error is showing (standalone or over a retained generation failure), no generation action is reachable, so a notation failure that recurs deterministically for the same phrase, width, and mode has no guaranteed in-app way out.** Per `decisions.md` D32's "Judged coherent" bullet: `Retry notation` re-engraves the same retained phrase's stored request at the current viewport and display mode, and `notation-error.ts` defines several failure codes that can repeat identically on retry for that reason -- not only a legibility-floor miss (`bp-tablet-landscape` and above fails hard at the current width if it can't fit at the legibility floor; below it, the same failure fires if even the two-system fallback doesn't fit) but also `notation_bounds_exceeded` and `notation_engraving_failed` (`vexflow-engraver.ts`), the latter of which wraps any unexpected engraving error and is not tied to viewport width at all -- so "resize the viewport" is not a general fix even where it would help the legibility-floor case specifically. While `notationError` is set, `primaryActionKind` (`WorkspaceHeader.vue`) never offers a generation action -- only `Retry notation` -- and the header is the only place `generate`, `regenerate`, or `retryGeneration` are ever invoked. So a player stuck on any of these codes has exactly two ways out, neither signalled as such: pick a different display mode that happens to engrave successfully (which clears `notationError` and restores `Retry generation` -- it does not itself start a new generation attempt), or switch instrument profile in a way that invalidates the retained phrase against the new range -- which, per the existing profile-switch-to-Empty exception, either triggers a fresh generation attempt (if the current rhythm combination is supported) or clears the phrase to **Empty** outright (if it is not), either of which ends the notation error by leaving the state it was attached to. If none of these applies, `Retry notation` can fail every time it is pressed, with no button anywhere that would start a new generation attempt instead. This applies equally to the standalone **Notation error** state and to **Notation error over a retained generation failure**. It has not been confirmed whether a real generated phrase can actually trigger any of these codes deterministically under typical supported settings (the Notation Contract and `notation-error.ts` allow for it structurally; whether current phrase/content bounds make it reachable in practice is unverified) -- but the design has no defined behavior for the case if it is reachable.
  - Option A (recommended): once `notationError` has persisted through some number of `Retry notation` attempts (or unconditionally, after the first), offer a way to abandon the retained phrase and start a fresh generation attempt -- e.g. a secondary action alongside `Retry notation`, or a fallback after N failed retries. Needs a product decision on the trigger condition and the action's label/placement; not decided here.
  - Option B: leave `Retry notation` as the sole action, but make its failure state itself explain that a display-mode switch or a different instrument profile may be needed to recover, so the player has a real signal instead of a silently repeating dead end. Smaller than Option A; does not add a way out, only a better explanation of the existing ones.
  - Option C: leave as-is, documented only. Not recommended if any of these codes is actually reachable at supported settings with real content -- a state with no confirmed way out is a worse outcome than a smaller copy nuance.
  - Recommendation: confirm reachability first (route to `coding-leader` or a content/engraving check, covering all three codes named above, not only the legibility floor), then decide between Option A and Option B if it is reachable. Not decided here -- this is a flow-level question, not a wording fix.
