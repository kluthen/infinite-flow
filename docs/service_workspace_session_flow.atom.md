# Workspace Session Flow

## INTENT
Coordinate the active phrase workspace as root-created, readonly in-memory session state, and the practice session the workspace runs from it, from the Start click to the session's end.

## THE RULE / LOGIC
A root-created Vue composable owns pending controls, current generation intent and result, presentation state kept separate from generation state, operation state, the "staff needs more room" notice state, and retryable error state for the active browser session. It exposes explicit control, profile, theme, notation, Generate, Regenerate, retry-generation, and retry-notation actions. Outside the room notice, ordinary control, musical-profile, theme, and notation edits never generate; an instrument-profile switch while a phrase is shown regenerates it. Under the room notice, an edit to a setting the phrase is generated from (tempo, the audio mix, the theme and notation edits excluded) reacts to it as the Idle fit round defines: under the too-many-notes cause it starts a retry round, an instrument-profile switch included; under the no-room cause it runs the phrase-independent room check, which can clear the notice into a new phrase, while an instrument-profile switch only changes the selection. Generate and Regenerate coordinate injected seed, request-identity, generation-outcome, fit-check, room-check, and notation-outcome seams; Regenerate retains pending controls and requests a new seed. Retry-generation is available only while idle with a captured generation error present; it does not require a retained failed intent. It builds a brand-new intent from the current controls and profile with a fresh injected seed and request identity -- the same construction Generate and Regenerate use -- rather than replaying the failed intent unchanged, so an edit made after the failure and before retrying is picked up; it applies the same unsupported-rhythm-settings block as Generate and Regenerate.

Every Idle generation -- Generate, Regenerate, Retry-generation, the regeneration an instrument-profile switch runs, and the runs the room notice and a phrase left too wide start by themselves -- is one fit run: one operation that may span several generation attempts, the first plus up to three fresh-seed retries, each with its own fresh seed and request identity, checked against the staff's room before anything is drawn. A staff layout failure (no room for the staff, or notes too wide for it) is never a retryable notation error: it goes to the room notice, to a replacement run, or, under a blocked rhythm-settings combination, to no phrase; only other notation failures are retryable notation errors.

A captured generation error, and a notation error, are cleared when the next fit run starts, whatever started it. The generation error is also cleared, along with the phrase and the room notice, whenever the workspace gives way to no phrase because the rhythm-settings combination blocks generation: an instrument-profile switch that would regenerate or start a round under a blocked combination, a width crossing that stops a run, and a room-notice change or a phrase left too wide that would need a replacement under a blocked combination. It is unaffected by ordinary control, musical-profile, theme, or notation edits made while idle outside the notice, by an instrument-profile switch made while no phrase and no notice show or under the no-room notice, both of which only change the selection, and by a no-room layout failure of the phrase on screen, which shows the notice with the banner in place. At most one operation runs at a time, a fit run counting as one operation however many attempts it makes. During an operation consumers can read but cannot mutate the exposed state. The composable coordinates outcomes without implementing Step 5 through Step 9 planners, engraving, or components, and never persists or restores user or session state.

The root also injects a window-width seam that tells whether the window is below the tablet-landscape layout's width. Every attempt of a fit run reads that seam when it builds its intent, and builds it with the note density the width gives at that moment, while the pending controls keep the chosen density. The unsupported-rhythm-settings block is judged on that same density at the moment the action is taken. The composable mirrors each crossing of that width in readonly state so the controls and the block follow the window at Idle. A crossing by itself never generates or regenerates; its only effect on the phrase is to stop a running fit run, as the Idle fit round defines, when it makes the combination one that blocks generation, leaving no phrase. The composable also listens to the staff's layout reports: at Idle, a change of the staff's layout inputs can clear the room notice into a new phrase, start a retry round under it, give the notice its no-room cause, have a phrase on screen that no longer fits replaced by a new one, or give way to no phrase under a blocked combination. The composable stops listening for crossings and for layout reports when the workspace is torn down.

The workspace composition root takes an injectable prewarm policy, enabled in production and disableable for tests and measurements. While it is enabled, the workspace posts a prewarm to the generation worker for the current controls, with the note density the window's width gives at that moment, when the generation worker starts, again after any rhythm control changes, including a profile switch that changes a rhythm control, and again after a crossing of the window's width that changes the note density that width gives. Prewarms are deduplicated by the resolved rhythm setting: one is posted only when that setting differs from the last one posted, so a non-rhythm edit, or a crossing that leaves the resolved density unchanged, posts none. Every prewarm carries one fixed seed and one fixed request identity and never draws from the injected seed or request-identity providers, so the seeds and request identities generation attempts receive are the same as with prewarm disabled. A prewarm is not a generation attempt: it gets no response and changes no phrase, intent, result, operation, or error state. Idle and a running session share the one generation worker, so both benefit from it.

The workspace also builds the practice session controller, which owns the one session the workspace runs at a time. Its module, with the measurement of phrase 1's staff fixed parts, loads as its own chunk on a createSessionController call the app root makes once at setup; until it has loaded no session can start, and a controller that arrives after the app is torn down is disposed of at once. The controller judges the start conditions from the Idle state, the window's shape, whether a session is running and whether the last session's review shows, and exposes the first condition that blocks a start. Start runs synchronously inside the player's Start click: it first discards the last session's kept review, then unlocks the audio, requests the screen wake lock and the landscape orientation lock (a refusal changes nothing), starts the audio transport and queues phrase 1's backing, then freezes the current controls and musical profile as the session's settings, holds the staff layout the window's width selects, opens the session history and starts the session runner, the count-in display, the audio-clock wake-ups and the end watchers; a throw at any step once the locks are requested undoes everything set up and propagates. From then on everything is driven by the audio clock, through an injected wake-up timer: the count-in display, the count-in's end, each phrase starting to sound and the engine's deadlines; every runner output is recorded in the session history. The fit check the runner is given judges each look-ahead phrase, with the intent of the attempt being checked, against the held staff layout and the current window's height budget, and the staff shows the session as the rolling display; a staff layout report after which a phrase shown or waiting no longer fits, or a failure of the session's staff, ends the session with the staff-not-shown cause. Every end takes one path: Stop, an interruption of the audio by the browser (ended with the stop cause), and what the end watchers report. The runner gets the end, then the scheduled events, the wake-ups, the audio, both locks and the end watchers are torn down, the session state returns to Idle, and the end's summary (cause, phase, number of phrases that started sounding) and the closed history are kept. An end once phrase 1 has started sounding then opens the last session's review over that closed history, shown in place of the staff, and, the staff's reports handed back to Idle, asks Idle for the next phrase through its fresh-phrase action (the Idle fit round's fresh run), without waiting for it; an end during the count-in opens no review and asks for nothing. While the review shows no session starts; closing it keeps it, and it can be shown again at Idle until the next start discards it. From start to end, the end watchers end the session for a hidden page (the hidden-tab cause), and for a window change or a staff layout report the session window rule rejects for the held layout, or any notation error of phrase 1's engraving (the staff-not-shown cause). An idle layout gate, kept in the entry chunk with no session logic, sits between the staff's reports (its layout inputs and each engraving's outcome) and the Idle machinery and always keeps the latest layout inputs; while a session runs, its end watchers divert the reports to themselves, so the Idle fit retries, room notice, regeneration and notation-error capture never act on phrase 1 during it, and at its end the reports are handed back and the latest inputs, then the last engraving outcome held, are re-applied to the Idle machinery. The staff's own session failure travels through the same gate but only ever to the session diverting the reports; with no session diverting it is dropped, never reaching the Idle machinery. A programming error propagates uncaught, after ending the session it belongs to if that session still runs.

The session controller also has a MIDI side, which loads with the controller, never in the entry chunk: its module comes with the controller's chunk, and the controller's load also loads the session runner (the engine and its failure ladder) through the workspace session's runner loader. From the controller's creation to its disposal the MIDI side follows the MIDI controller's state and every played note, handles every time on the audio clock and sets every timer on the session's audio-time agenda. At Idle it names phrase 1's starting note, its first fresh attack, exactly while Start may be clicked, the MIDI controller is connected, the connection sheet is closed and the staff shows Idle's phrase; a played note with exactly that concert pitch, octave included, starts the session through the controller's own start, the path the Start click takes, so every start condition, lock and count-in is the same, and any other note at Idle does nothing. The session's mode is fixed at its start by the MIDI controller's state: connected gives a session with a controller, which reads every note until it ends; any other state gives a session without a controller, which reads no note and sets no MIDI timer for its whole run, count-in included, even if a device attaches afterwards. When the selected controller is away at that start, the MIDI side holds the MIDI controller's reattachment, so the same device coming back is neither opened nor read until the session ends, and the teardown releases the hold; a port still opening at the start holds nothing. A session with a controller keeps one acknowledgement over the expected notes of every phrase readied so far, each phrase's from its own first downbeat: each played note, its onset latency-compensated with the USB correction for every controller, is matched at most once; a match is recorded in the history and published for the score to light, and a note that matches nothing leaves no trace. Every finished played note is recorded in the history with its onset and release compensated by the same total, so the history's played notes line up with the generated notes the player heard. The silence timer is armed by the first note played (in a session the starting note started, the starting note itself, from its onset), re-armed by every played note whether it matches or not, and suspended while the controller is lost; the session ends with the silence-timeout cause once the audio clock is strictly past 30 seconds after the last arming, and a session in which no note is ever played never times out. During a session with a controller any state other than connected is a loss: a 30-second countdown runs from the audio time of the loss, published second by second, and at 0 ends the session with the controller-lost cause, which ends on screen exactly as a silence timeout does. When the same device is connected again before then, every expected note whose onset fell between the loss and the reattachment is passed over, never acknowledged afterwards even if its window is still open, then the countdown clears and a silence timer that was armed is re-armed from the reattachment. Every end, whatever its cause, first ends the notes still held on the controller at the current audio time and records them in the history, before the runner gets the end and the engine's end closes the history; the teardown then stops the MIDI side, dropping its timers, clearing the countdown and the acknowledged notes and releasing a held reattachment. A throw inside the MIDI side's handling of a note or of a state change is a programming error that ends the session loudly.

## TECHNICAL INTERFACE
The root creates the composable with injected seed, request-identity, window-width, generation, and notation outcome seams, plus a fit check (does a generated phrase fit the staff's current layout inputs, drawing nothing), a room check (does the staff have room at all with a given key signature), the staff's layout-input reports, and a required seam that drops whatever the notation seam presents. Consumers receive readonly pending-control, note-density context (where the window stands against the tablet-landscape layout's width, and whether the density has stepped down, always false at Idle), intent/result, presentation, operation, and error state, the room notice's cause (no room, notes too wide, or none), whether retries are running, and a room-notice announcement count, plus explicit actions (among them startFreshPhrase, the fresh run a session end asks for) and a teardown that stops listening for window-width crossings and layout reports; no storage API is part of the interface. The workspace session also exposes createSessionRunner({ start, checkFit, now, onOutput, onError }), which starts a session runner from the given session start, fit check (given the candidate's successful outcome with the intent of its attempt, and its phrase number), audio clock, and output and error sinks, bound to the same generation seam, seed and request-identity providers, and window-width seam the Idle flow uses, so a running session and the Idle flow share the app's one generation worker. The workspace composition root also takes an injectable prewarm policy, enabled by default in production, which tests and measurements can disable. The workspace session also exposes createSessionController(), which loads the controller's chunk and returns a session controller built over the Idle state and its startFreshPhrase action, the audio transport, the session browser ports (wake lock, orientation lock, page visibility, window shape), the runner factory, the session clock (a wake-up timer factory, a wall clock and a frame loop), the idle layout gate's port, the measurement of phrase 1's staff fixed parts and a loader of the engraver's staff planner (loadSessionStaffFitPlanner, beside that measurement), which the session's fit checks use. The controller exposes readonly state (its phase: idle, count-in or running; the count-in display; the struggling notice; the locked session tempo; the held staff layout; canStart and the first start blocker; the staff the session shows and the highest phrase number it has readied, both null outside a session; the last end's summary and closed history; the last session's review, its closed history and whether it shows, or null when none exists), a query telling whether a phrase is on screen, and five actions: start (synchronous, for the Start click; throws while a start condition does not hold), stop (throws with no session running), closeReview (throws unless the review shows), showReview (throws unless a review exists, does not show, and no session runs) and dispose (ends a running session, stops reading the window and frees the wake-up timer). The staff's reports reach the Idle machinery through the idle layout gate's handlers, which the workspace exposes as handleLayoutInputs, handleEngraved, handleNotationError and handleSessionStaffFailed. The controller's MIDI side is createSessionMidi(deps), in its own module loaded with the controller; the runner's module is loaded by the workspace session's loadSessionRunner(), which createSessionController() calls as part of the controller's load. createSessionMidi reads the MIDI controller, the audio transport, whether the connection sheet is open and whether Start may be clicked, the Idle result and the written phrase the staff shows, and the controller's own start. It exposes readonly readings (the starting note or null, the controller-lost countdown as seconds left or null, the acknowledged expected notes, and whether the running session has a controller, null outside a session), which the controller's readonly state publishes, plus beginSession(seams), given the session's tempo, phrase 1's concert timeline, history, agenda, an end-for-a-cause and a fail-loudly sink, which returns phraseReady (add a readied phrase's expected notes), releaseHeld (end every held note now, before the engine's end) and stop (the teardown), and dispose. The session end causes add silence-timeout and controller-lost. The MIDI controller exposes holdReattachment() and releaseReattachment() for the hold of a session started while it is away. The session history takes recordPlayedNote (a finished note with compensated onset and release) and recordAcknowledgement (one acknowledged expected note), and each phrase record reads back its acknowledgements and played notes.

## EXPECTATION
Consumers cannot mutate workspace state directly. Outside the room notice, ordinary edits produce no generation request; under it, only an edit to a setting the phrase is generated from can start a run, as the Idle fit round defines. Generate and Regenerate each start one fit run through injected seams, one operation of up to four attempts issued one intent at a time. A regenerate operation preserves controls and uses a renewed seed. Retry generation is available only while idle after a captured generation error, is blocked under an unsupported rhythm setting exactly like Generate and Regenerate, and issues a brand-new intent built from the current controls and profile with a fresh seed and request identity rather than replaying the failed attempt, so a control edit made after the failure and before retrying is reflected in the retried request. A staff layout failure never shows the retryable notation error. The captured generation error remains visible through any control, musical-profile, theme, or notation edit made while idle outside the notice, through an instrument-profile switch made while no phrase and no notice show or under the no-room notice, and through a no-room layout failure of the phrase on screen; it clears once the next fit run begins, whatever started it, or when the workspace gives way to no phrase under a blocked rhythm combination. Reloading or a later browser session restores no controls, intent, result, presentation preference, operation state, room notice, or error. Every intent carries the note density the window's width gave when it was built. A crossing of that width updates the readonly note-density context, never issues a generation request, and changes the phrase on screen only by stopping a running fit run it blocks, leaving no phrase. The room notice's cause, whether retries are running and the announcement count are readonly. With the prewarm policy enabled, the generation worker's start and each change of the width-resolved rhythm setting, whether by a rhythm control change, a profile switch that changes one, or a width crossing that changes the resolved note density, post exactly one prewarm for the current width-resolved controls, and no other edit or crossing posts one; with it disabled no prewarm is posted. A prewarm never issues a generation request, changes the phrase on screen, or consumes a seed or request identity from the injected providers. Building the session controller requests no lock and opens no audio; no session can start before its chunk has loaded. A start inside the Start click unlocks the audio and requests both locks, and a start that fails part-way leaves nothing acquired. Every end, whatever its cause, ends the runner, releases both locks, stops the wake-ups, fades the audio out unless the transport already stopped it, stops the end watchers and returns the session state to Idle exactly once; a second cause arriving in the same tick ends nothing more. While a session runs no staff report reaches the Idle machinery; at its end the latest layout inputs and the held engraving outcome are re-applied. After an end once phrase 1 has started sounding, the review opens over the closed history and Idle starts a fresh phrase at once; no session starts while the review shows, and the next accepted start discards it. An end during the count-in opens no review and generates nothing. A played note at Idle starts a session, exactly as the Start click does, only when it is the named starting note; any other note at Idle does nothing. A session started while the MIDI controller is not connected reads no note, never times out and never counts down, and a selected controller away at its start is neither reopened nor read until the session ends. In a session with a controller each played note is acknowledged at most once, every finished note reaches the history with compensated onset and release, more than 30 seconds without a played note after the first ends it with silence-timeout, and a loss not recovered within 30 seconds ends it with controller-lost; when the same device returns, no expected note that fell due during the loss is ever acknowledged, and later notes are acknowledged as usual. Notes still held at any end are recorded before the history closes. Neither the MIDI side nor the session runner is in the entry chunk.
