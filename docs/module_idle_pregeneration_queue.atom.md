# Idle Pre-Generation Queue

## INTENT
Run pre-generation at Idle as a background queue on the one generation worker that always gives way to the player, keeps its ready phrases in memory only, and hands them to Start.

## THE RULE / LOGIC
Parts. Around the pure plan ([[module_session_pregeneration_plan]]), the queue has two parts: a workspace orchestrator, loaded lazily in the session controller's chunk, which runs the plan's attempts on the generation worker client, checks each successful attempt's fit, holds the ready phrases (at most four, phrases 2 to 5) in memory and hands them to Start; and an Idle background slot, a tiny part of the entry chunk, through which the Idle flow yields to the player. An injectable pre-generation policy, enabled in production and switched off from the page URL for measurements, turns the whole queue off: under it the orchestrator never runs and Start takes nothing.

Abort signals. Only background attempts carry an abort signal: one abort controller per attempt, owned by the orchestrator and held in the slot while the attempt is in flight, the slot holding at most one. The Idle flow's player requests (Generate, Regenerate, retry, the regeneration of a profile or instrument switch, the room notice's and the replacement runs, the fresh phrase 1 after a session) still pass none and are never cancelled. The Idle flow's generate seam calls the background slot's yield to the player synchronously before posting every player request at Idle, which aborts the background attempt in flight, if any, so the worker client's existing cancellation replaces the worker and the player's request never waits behind it ([[module_generation_worker_cancellation]], its mechanism unchanged). The orchestrator also aborts the attempt in flight at Start's take, at a discard, at a window re-check that shrinks the queue or crosses the tablet-landscape width, when the run conditions stop holding, and at teardown. A cancelled background attempt is prewarmed exactly as the client prewarms any cancellation: with the prewarm policy enabled, the fresh worker receives a prewarm of the cancelled intent after the re-posted requests. The worker builds a prewarm in budgeted slices between messages and answers a generate request as soon as it arrives, so that prewarm delays the player by at most about one slice; and without a Vary settings landing the cancelled intent's rhythm setting is phrase 1's own, the one both the player's next request and the restarted pre-generation use.

Not an operation, not a prewarm. A background attempt is not an operation of the Idle generation session: it sets no operation state, locks no edit, and is never "a new phrase being generated" for Start, so the start facts' generation-running fact never counts it. Nor is it a prewarm: it uses the plan's seeds and real request ids, never the prewarm's fixed seed and request id. The plan starts from phrase 1 and the Idle choices as a session would take them, the session settings built from phrase 1's intent as Start builds them, so a phrase pre-generated with my instrument selected carries its profile. Pre-generation starts only after the workspace has posted its prewarm, which it does when the generation session is created, on the same worker.

When it runs. Only while the policy is enabled and every session start condition holds, that is while the controller's start blocker is none: no session running, no review showing, phrase 1 drawn, no Idle operation running, no notation error, no generation failure reported, rhythm settings that allow generation, the staff shown and no room notice. When they stop holding, the attempt in flight is aborted and the ready phrases are kept; when they hold again, the ready phrases are re-validated and re-checked as at a window change, and pre-generation resumes after the last one kept. So nothing runs while a review shows, and it stops and resumes around one. A stale phrase 1 is no reason to stop: the stale-phrase prompt is not a start condition, so the queue keeps running while phrase 1 is stale and while the prompt shows, building, through the plan, exactly the phrases the session plays if the player uses that phrase 1. The queue has no quiet stop: an error met while the plan is built or stepped, a carry-in error included, is a programming error, handled as any other: the attempt in flight is aborted, the queue emptied, the error reported out of band as an unhandled error, and the queue stays stopped until its key next changes. Nothing is ever saved: the queue lives in memory only and is gone on reload.

Discards. The queue belongs to one key: phrase 1 (its Idle result, and so its session seed), the generation controls except tempo, the instrument among them, the musical-profile selection, Vary settings and Tension across phrases. The orchestrator watches that key reactively rather than being called from each Idle action. Any change of it (a control, the profile, the instrument, a regeneration or any other new phrase 1, either session option) aborts the attempt in flight and empties the queue at once, and pre-generation starts again from the new phrase 1 once the change is over, since one Idle action may change several parts of the key in a row. Tempo and Rising tempo are not in the key and discard nothing: a ready phrase made before a tempo change is kept, and its intent takes the tempo in effect when Start takes it, the tempo changing nothing generated. Nor are my instrument's clef and display name, which no phrase is generated from. What discards is the same with a stale phrase 1: the key still holds phrase 1 and the current settings, so any change of a setting phrases are generated from discards the queue, and the prompt's Regenerate discards it by replacing phrase 1; showing, answering or dismissing the prompt discards nothing by itself.

Layout changes. On every staff layout report, received through a passive observer on the idle layout gate's port, the gate being otherwise unchanged, and on every crossing of the tablet-landscape layout's width, the orchestrator re-checks the ready phrases in order: it re-derives each one's intent with the window read now (the density step-down) and re-checks its fit against the layout a session would hold now, the held layout from the window's shape at that moment and the staff's latest layout inputs, through the same staff fit planner and the same held-layout fit function the session's display fit uses, shared rather than duplicated. The first ready phrase whose intent no longer matches, or that no longer fits, is discarded with every phrase after it, and pre-generation resumes from there; a crossing also aborts the attempt in flight, whose request may have changed, and a phrase that stopped the plan is tried again. The same re-check runs for a layout change from any other cause: the orchestrator watches the Idle session's my instrument, and every saved change to it that does not discard the queue (a change of its clef, its name, or its range while another profile is selected) re-checks the ready phrases the same way, since it may change the staff's shared height or the clef a session draws in; a change that replaces phrase 1 discards the queue through its key instead. Every fit check draws the phrase in the clef a session would draw it in, the selected instrument's. None of these re-checks runs while a session runs: a staff layout report or a crossing of the width during a session re-checks nothing and leaves the ready phrases as they are, and the re-check runs on the return to Idle instead, when the run conditions hold again, as above.

Start. Start takes the queue from the orchestrator: the take aborts the attempt in flight, gives each ready phrase's intent the tempo in effect, re-checks the ready phrases' fit synchronously against the start's held layout, drops from the first that does not fit, and passes the rest to the session runner in the session start, where the session engine spends each one whose intent it re-derives identically, in place of requesting it. The stale-phrase prompt's Use it takes the queue exactly as Start does. Start never waits for a background attempt. The take does not empty the queue, so a count-in that ends back at Idle on the same phrase 1 reuses it; topping it up resumes only at Idle, and nothing is topped up during a session.

## TECHNICAL INTERFACE
`src/components/workspace/workspace-pregeneration.ts`, the orchestrator, in the session controller's chunk: `createWorkspacePregeneration(dependencies)` returns `{ take(heldLayout), recheck(), dispose() }`; the session controller builds it over its start blocker, its two session flags, the Idle state, the window's shape and the idle layout gate's port, and its programming errors are thrown out of band. `src/composables/generation-session-pregeneration.ts`, the Idle background slot in the entry chunk: `createPregenerationSlot()` gives `{ hold(abort), yieldToPlayer() }`, and `yieldingToPlayer(slot, generate)` is the Idle flow's generate seam, which calls `yieldToPlayer()` before each player request it posts at Idle. The pre-generation policy, `enabled` or `disabled`, is injectable at the workspace composition (`pregenerationPolicy`); production reads it from the page URL with `pregenerationPolicyFromSearch` in `src/components/workspace/prewarm-policy.ts`, beside the prewarm switch: `?pregeneration=off` disables it, `?pregeneration=on` or no such parameter enables it, and any other value throws. The e2e workspace harness defaults it to off, unless it is built with `VITE_HARNESS_PREGENERATION=on`, under which an e2e lane runs the suite with pre-generation on; its pre-generation spec turns it on with `?pregeneration=on`, and the specs that need it off load `?pregeneration=off`. Background attempts pass their signal to `generate(intent, signal)` of the client in `src/generation-worker/generation-worker-client.ts`. The run conditions are the controller's start blocker (`sessionStartBlocker`, `src/session/session-start-conditions.ts`); the held layout comes from `sessionLayoutAtStart` (`src/session/session-window.ts`); the fit check is `fitsHeldLayout` with `writtenPhraseOf` (`src/components/workspace/held-layout-fit.ts`), shared with the session's display fit; layout reports come through the idle layout gate's `observeInputs`, acted on only outside a session. `recheck()` runs the layout re-check on demand, for a layout change the staff's reports do not carry; nothing calls it: the orchestrator watches the Idle session's my instrument itself. The plan's settings come from sessionSettingsAtStart(…, phraseOne.intent) (src/session/session-intents.ts), and phrase 1's own settings from phraseOneSettings(phraseOne.settings, phraseOne.intent, tempo) (src/session/stale-phrase-one.ts), as Start passes them, and the fit check's clef from instrumentClefOf (src/domain/profile/instrument-clef.ts). Start (`src/components/workspace/workspace-session-start.ts`, then `workspace-session-begin.ts`) calls `take(heldLayout)` and passes the result as `SessionStart.readyPhrases`.

## EXPECTATION
- With the policy enabled and every start condition holding at Idle, up to four phrases following phrase 1 are generated one after another in the background, after the prewarm, on the same worker; with the policy off, none is.
- A player request at Idle while a background attempt runs aborts that attempt first and is answered as fast as with pre-generation off; a player request is never cancelled.
- A background attempt sets no operation state, locks no edit and never blocks Start; Start pressed while one runs starts at once.
- A change of a control, the profile, the instrument, either session option or phrase 1 empties the queue; a change of tempo or Rising tempo keeps it, and Start gives the kept phrases the tempo in effect.
- A window change that changes the density or the held layout discards from the first ready phrase that no longer matches or fits, and pre-generation resumes from there.
- A save of my instrument that changes the staff's shared height or its clef without discarding the queue re-checks the ready phrases as a window change does: one that no longer fits is discarded with every phrase after it; one that fits stays.
- With my instrument selected, the pre-generation's settings carry its profile, and a pre-generated phrase taken at Start lies in its concert range.
- Nothing runs while a review shows or any start condition fails; the ready phrases are kept and pre-generation resumes after the last one.
- Nothing is written to storage; the queue is gone on reload.
- With a stale phrase 1, pre-generation keeps running, the prompt showing or not, and Use it takes the ready phrases as Start does; no carry-in error stops it quietly.
- A stale phrase 1 changes nothing in what discards the queue: a settings change or Regenerate empties it; the prompt alone does not.
- A staff layout report or a width crossing during a session leaves the ready phrases alone; they are re-checked on the return to Idle.
