# Review Export Pipeline

## INTENT
Turn the session the Review shows, the session that just ended or a kept session read back, into exactly one export file per player action, built in the page on demand and handed to the browser as a download, with nothing sent and nothing stored by the export.

## THE RULE / LOGIC
The pipeline runs from the session the Review shows to a browser download. Its input is what the Review draws that session from: the closed history of the session that just ended, or a kept session decoded by the kept-session codec once read back by its key; either way its phrases in session order, each with its clef, and its recorded start time, read only; nothing is generated again. The Review offers one action per content. Export generated notes comes with a format choice, MusicXML or MIDI, and, for MIDI only, a backing-track choice. Both actions export the scope the Review holds, Whole session or Favorites only; Favorites only is disabled, saying why, while the session has no favorite. The scope starts at Whole session at every Review, returns to it as soon as the session's last favorite goes, and is never saved. Export played notes shows only when the history holds at least one played note within a phrase or, in a Jam, the doodle holds a raw doodle note, a very short one included, which is read without loading the export code. It is disabled while the file it would build under the scope holds no note, which is read the same way, the doodle's raw notes counting in either scope and never as a favorite, so an export never fails for want of a note, and it gives the first reason that applies: in a Jam whose code failed to load, that failure; under Favorites only, no favorite phrase holding a played note and, in a Jam, no raw doodle note either, then every played note in them (in a Jam, its favorites' and its doodle's) very short with Include very short notes off; under Whole session, every played note very short with Include very short notes off. One activation builds exactly one file and starts one download.

Each action first loads the export code (the history's encoder adapters, the three encoders and the backing renderer) on demand, in one chunk outside the entry chunk, through a single lazy boundary: later exports share one load, and after a failed load the next export tries the load again. It then takes the phrases the scope picks: under Whole session every phrase as it is; under Favorites only the favorite phrases, as the activation read them, in session order with their session phrase numbers, laid out back to back from the first one's start, each run of phrases that followed each other in the session moving as one and cut at its end when the next phrase is not exported, so a played note held past that end stops there and one played after it is left out. Very short notes are judged by their length as played, before that cut. Both contents use this one selection, so the two files of one scope line up. The encoders place each phrase by its position in the file, its number kept for its marker, rehearsal mark and measure numbers. In a Jam session, each file opens with a Doodle section built by Jam's code (module_jam_code_boundary), which the file builders take as data and never import: the doodle's measures at its capture tempo from time zero, the first exported phrase at the next barline, in both scopes, the doodle never a favorite. An export asked for while Jam's code loads waits in its own loading state; when that load has failed, both exports are disabled, each naming why after it, and an export already waiting ends there with nothing built and no export error. It then builds the file it was asked for:
- generated notes as MusicXML: the history's MusicXML adapter, then the MusicXML encoder, as UTF-8 bytes, in the written pitch of the session's instrument profile, each phrase in the clef its record carries; the backing-track choice is ignored;
- generated notes as MIDI: the history's MIDI adapter, given the backing renderer's notes for each phrase's stored harmony only when the backing track is asked for, then the generated-notes MIDI encoder, at concert pitch;
- played notes as MIDI: the history's records with their very short notes left out, unless Include very short notes is on, then the history's played-notes adapter, then the played-notes MIDI encoder; in a Jam, its Doodle section holds the raw doodle notes, unquantized, a note held past the doodle's end stopped there, and none in a Jam on a kept doodle.
No played note, a raw doodle note included, reaches a generated-notes file, and the played-notes file holds only played notes: the two contents are never merged into one file.

Every file name starts with the session's stem, infinite-flow-{YYYY-MM-DD}-{HHmmss}, from the session's recorded start in the player's local time, never the time of the export, then -generated.musicxml, -generated.mid or -played.mid, with -favorites added before the extension under Favorites only, so the files of one session sort together and are told apart. The same history and request, scope included, always give the same name and the same bytes, and a Whole session export of a session that is no Jam is byte for byte what it was before the scope and the doodle existed.

The built file is handed to the browser as a download of its bytes, with its MIME type, under its file name. Any failure on the way (the export code failing to load, an adapter's or an encoder's typed error, the browser refusing the download) rejects that export, Jam's code failing to load never being one of them, and the Review shows its one export error until the next export of either content starts; a failure before the download downloads nothing. A successful export shows and announces nothing: the browser's download is the confirmation.

The Review and the file live in memory only, and the pipeline stores nothing: the file is never kept, and the session itself is kept only by the session's own save at its end, never by the export. Nothing is sent; the format and backing-track choices are the player's review preferences, saved as settings when the player changes them, and Include very short notes, off at first, is held for the page visit only and never saved, as the scope is. The download the player starts is the only way a session's data leaves the page.

## TECHNICAL INTERFACE
exportGeneratedNotes(history, request, ports, doodle), its request a GeneratedNotesExportRequest { format, backingTrack, scope } and doodle an ExportDoodleSection or null, and exportPlayedNotes(history, request, ports, doodle), its request a PlayedNotesExportRequest { includeVeryShortNotes, scope } and doodle a PlayedNotesDoodleSection or null, in src/components/workspace/review-export.ts each run one export of an ExportableHistory (src/export/export-file.ts: phrases() and startedAt, given alike by a live history and a decoded kept session) over ReviewExportPorts { load, download }, by default the page's own from browserReviewExportPorts(document). The scope is an ExportScope (src/export/export-file.ts): { kind: 'wholeSession' } (WHOLE_SESSION) or { kind: 'favoritesOnly', favorites }, the favorite phrases' numbers. In src/components/workspace/played-notes-availability.ts, historyHoldsPlayedNote(records) tells, without loading the export code, whether a phrase holds a played note; playedNotesFileHoldsNote(records, request, doodleNotes) whether its file would hold a note under the request's scope, a Jam's raw doodle notes counting, the action being disabled while it would not; and playedNotesUnavailable(records, request, jam), jam a PlayedNotesJam { doodleNotes, codeFailed } or null, why not, a PlayedNotesUnavailable ('doodleNotLoaded', 'noPlayedNoteInFavorites', 'everyFavoriteNoteVeryShort', 'everyFavoriteAndDoodleNoteVeryShort' or 'everyNoteVeryShort', src/components/review/review-types.ts) or null; a GeneratedNotesUnavailable ('doodleNotLoaded') or null says why the generated-notes export is disabled; they read the records through recordsWithoutVeryShortNotes (src/domain/played-notes/stray-notes.ts) as the request asks. phrasesInScope(records, scope) in src/export/favorites-selection.ts is the selection, throwing a FavoritesSelectionError for a favorites-only scope with no favorite or with a favorite the session does not hold. useReviewExports in src/components/workspace/use-review-exports.ts, composed into the review area (src/components/workspace/use-review-area.ts), runs these for the session the Review shows: the played-notes action shows when holdsPlayedNote does (a phrase's played note, or a Jam's raw doodle note); it waits for Jam's code to settle for a Jam session's export (settledJamCode, src/components/workspace/use-review-jam-code.ts) and asks it for the doodle's sections, exportDoodleSection(doodle, phraseOne) and exportPlayedDoodleSection(doodle) in src/jam/export/doodle-section.ts; it holds the Review's scope (scope, setScope; a ReviewExportScope, 'wholeSession' or 'favoritesOnly', refusing favorites only with no favorite), builds each request from it, and reads Include very short notes as the Review host (src/components/workspace/use-review-host.ts) holds it for the page; the generated-notes ExportRequest from the panel names the scope; src/components/review/ReviewScope.vue is review-scope. useReviewExportAction in src/components/review/use-review-export-action.ts holds one export button's state: loading and disabled while its file is built, the Review's one export error set on a failure and cleared as the next export starts. loadGeneratedNotesExport() in src/export/load-generated-notes-export.ts is the lazy boundary, rejecting with a GeneratedNotesExportLoadError on a failed load. buildGeneratedNotesFile(history, request, scope, doodle), with request { format: 'musicxml' | 'midi', backingTrack: boolean }, and generatedNotesFileName(startedAt, format, scope) are in src/export/generated-notes-file.ts; buildPlayedNotesFile(history, options, scope, doodle), options { includeVeryShortNotes } leaving very short notes out by default, and playedNotesFileName(startedAt, scope) are in src/export/played-notes-file.ts, the scope defaulting to the whole session; exportFileStem, scopeNameSuffix, ExportDoodleSection and ExportFile { fileName, mimeType, bytes } are in src/export/export-file.ts. The files are built from the history's adapters musicXmlInputFromHistory, midiInputFromHistory and playedNotesMidiInputFromHistory (src/session/session-history-export.ts) and the encoders encodeGeneratedNotesMusicXml, encodeGeneratedNotesMidi and encodePlayedNotesMidi, whose input checks accept any rising session phrase numbers from 1. The MIME types are application/vnd.recordare.musicxml+xml for MusicXML and audio/midi for both MIDI files. downloadFile(file, document) in src/export/browser-download.ts makes the download, refusing a document with no window with a BrowserDownloadError.

## EXPECTATION
- One export activation downloads exactly one file, of the content, format and scope asked for.
- The MusicXML file is in the session profile's written pitch and never holds a backing; the generated-notes MIDI file is at concert pitch and holds the backing track only when it is asked for; neither generated-notes file holds a played note.
- The played-notes action shows only when the history holds a played note within a phrase or, in a Jam, the doodle holds a raw doodle note, very short ones included, and its file holds the played notes only: by default without the very short ones, and every one as received with Include very short notes.
- The played-notes action is disabled while its file would hold no note under the scope, with the first reason that applies, and the export never reaches the encoder's no-played-note error.
- Under Favorites only, each file holds exactly the favorite phrases, in session order with their session numbers, back to back from time zero; a played note held past a favorite phrase is stopped at its end when the next phrase is not exported; the two MIDI files of one scope share the tempo map and markers.
- Favorites only is disabled, with its reason, while the session has no favorite; the scope starts at Whole session at every Review and is never saved.
- A Whole session export of a session that is no Jam is byte-identical to the same export before the scope and the doodle existed.
- A Jam session's files open with the Doodle section, from time zero at the doodle's capture tempo, the first exported phrase at the next barline, in both scopes; only the played-notes file holds raw doodle notes.
- After a failed load of Jam's code, a Jam session's two exports are disabled, each naming why after it, the other export controls live; an export pressed while it loaded ends there, never in the Review's export error.
- File names come from the session's recorded start, never the export's time, and end in -generated.musicxml, -generated.mid or -played.mid, with -favorites before the extension under Favorites only.
- The same history and request give the same file name and bytes every time.
- The export code is outside the entry chunk and is loaded once for every later export; after a failed load the next export loads it again.
- Any failure rejects the export and shows the Review's export error, which the next export removes as it starts; a failure before the download downloads nothing.
- An export of a kept session read back after a reload is byte-identical to the same export before the reload.
- Nothing from the session or the file is sent over the network, and the export writes nothing to browser storage; the export choices are sent nowhere; the format and backing track are kept only as the player's saved review preferences, and Include very short notes and the scope are never saved.
