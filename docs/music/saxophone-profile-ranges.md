# Adopted Saxophone Range and Display Profiles

Infinite Flow adopts three declarative, concert-pitch instrument profiles: **C MIDI keyboard `48-72`**, **B-flat tenor saxophone `46-70`**, and **E-flat alto saxophone `51-75`**, with every endpoint inclusive. The saxophone choices deliberately give both instruments the same written working range, C4-C6, while their different transpositions yield distinct sounding MIDI ranges; they are conservative product defaults, not claims about every player's physical limits. Each profile uses the same phrase-wide overlapping register policy: Low, Middle, or High is a hard window selected once for the complete **four-measure** phrase, never per note or bar. Notation remains an independent view of the immutable concert timeline, using Concert `+0`, B-flat `+14 semitones/+8 diatonic steps`, or E-flat `+9/+5`, with B-flat selected initially. This resolves O15 and does not imply that selecting an alto or tenor profile changes notation mode, or vice versa. On a post-generation profile switch, retain a phrase only if every unchanged concert event fits both the new active range and the whole-phrase window required by the current Register selection; otherwise retain controls, select a fresh seed, and regenerate the complete phrase. Never transpose source events to fit.

## Conventional compass supports a conservative shared written policy

**Cited fact:** modern commonly used alto and tenor saxophones share a conventional written compass of **B-flat3 through F-sharp6**, excluding altissimo; tenor sounds a major ninth below its written part and alto a major sixth below it ([Encyclopaedia Britannica](https://www.britannica.com/art/saxophone)). With the adopted `C4 = MIDI 60` convention, that full written compass is MIDI `58-90`, which converts exactly to concert MIDI **`44-76` for tenor** and **`49-81` for alto** ([Scientific pitch notation](https://en.wikipedia.org/wiki/Scientific_pitch_notation); [Encyclopaedia Britannica](https://www.britannica.com/art/saxophone)). These are source-backed physical/notated compass facts, not suitable first-release generator limits: the research does not establish a universal comfortable phrase range across technique, equipment, articulation, dynamic, or player level.

**Adopted product policy:** written **C4-C6** is the shared first-release saxophone working range. It is exactly two octaves, stays within the documented non-altissimo compass, and leaves the documented lower and upper edge pitches outside the generator's default vocabulary ([Saxophone range research](Saxophone%20profile%20ranges/saxophone-ranges.md)). Applying the conventional sounding offsets yields tenor concert **B-flat2-B-flat4, MIDI `46-70`**, and alto concert **E-flat3-E-flat5, MIDI `51-75`**. Treat each range as inclusive integer data, so each span is 24 semitones and contains 25 legal chromatic pitches. This is a common policy shape, not a shared concert range: preserving a common written register is the musician-facing benefit, while concert MIDI remains the generator's unambiguous source representation.

| Adopted declarative profile | Active concert MIDI, inclusive | Corresponding written working range | Status and rationale |
| --- | --- | --- | --- |
| C MIDI keyboard | `48-72` | Concert display; `C3-C5` under C4 = 60 | Adopted first-release profile ([First-release specification](../../specs/first-release-master-spec.md)). |
| B-flat tenor saxophone | `46-70` | `C4-C6` when displayed as B-flat tenor | Adopted conservative first-release profile; subtract 14 semitones from written MIDI. |
| E-flat alto saxophone | `51-75` | `C4-C6` when displayed as E-flat alto | Adopted conservative first-release profile; subtract 9 semitones from written MIDI. |

## Overlapping windows preserve route for contour and recovery

**Adopted product policy:** `overlapping-three-window-v1` applies to every profile. For inclusive active endpoints `[lo, hi]`, let `W = hi - lo` and `S = max(12, ceil(W / 2))`; derive `Low = [lo, lo + S]`, `Middle = [lo + floor((W - S) / 2), lo + floor((W - S) / 2) + S]`, and `High = [hi - S, hi]`. Every adopted profile has `W = 24`, therefore `S = 12`: each register supplies 13 legal MIDI pitches and the adjacent windows overlap by seven pitch positions. This common calculation makes the range decision pure profile data rather than tenor-, alto-, or keyboard-specific planner code ([Instrument Profile](../entity_instrument_profile.atom.md); [Phrase Generation Profile Policy](../module_phrase_generation_profile_policy.atom.md)).

| Profile | Low window | Middle window | High window |
| --- | --- | --- | --- |
| C MIDI keyboard | `48-60` | `54-66` | `60-72` |
| B-flat tenor saxophone | `46-58` | `52-64` | `58-70` |
| E-flat alto saxophone | `51-63` | `57-69` | `63-75` |

**Cited fact:** Infinite Flow defines the result as one coherent four-measure object, requires range, contour, leapiness, and recovery to outrank expressive ranking, and requires the planner to reserve active range for an outward leap's required contrary recovery ([First-release specification](../../specs/first-release-master-spec.md); [Leap Recovery](../rule_leap_recovery.atom.md)). **Policy implication:** every pitch-planning run receives one already-resolved Low, Middle, or High window and applies it as a hard filter for the whole phrase. Fixed register creates one such run; Varying creates separately resolved candidate runs and selects only among windows for which the bounded complete pipeline produces a valid phrase. It cannot change window mid-phrase, silently widen a window, waive recovery, or relax contour, grammar, cadence, or range. The overlap is a deliberate helpful policy rather than a guarantee of feasibility: compared with disjoint thirds, it usually leaves more room to approach a boundary, make an allowed leap, and turn back by the mandatory 1-4 semitone contrary recovery ([Register-window research](Saxophone%20profile%20ranges/register-windows.md); [Leap Recovery](../rule_leap_recovery.atom.md)).

## Signed display transforms belong only in notation

**Cited fact:** tenor is a B-flat instrument whose written C sounds B-flat, while alto is an E-flat instrument whose written C sounds E-flat ([Yamaha](https://www.yamaha.com/en/musical_instrument_guide/saxophone/play/play003.html)). Tenor sounds a major ninth below written pitch and alto a major sixth below written pitch ([Encyclopaedia Britannica](https://www.britannica.com/art/saxophone)). MusicXML explicitly represents transposition as a written-to-sounding relationship and separates chromatic, diatonic, and octave displacement so engraving can preserve correct enharmonic spelling ([MusicXML transpose](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/transpose/); [MusicXML diatonic](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/diatonic/)).

**Adopted renderer policy:** store the following signed transforms as display-convention data and apply them only after generation. All three use treble `G2` clef; Concert `G2` is a uniform product convention for this single-staff view, not a universal concert-score assertion.

| Display convention | Concert-to-written transform | Inverse written-to-sounding interchange values | Required display behavior |
| --- | --- | --- | --- |
| Concert | `0 chromatic semitones`, `0 diatonic steps` | `chromatic=0`, `diatonic=0`, no octave change | Retain concert spelling and use `G2` under the adopted display convention. |
| B-flat tenor | **`+14 chromatic semitones`, `+8 diatonic steps`** | `chromatic=-2`, `diatonic=-1`, `octave-change=-1` | Write a major ninth above concert in `G2`; transpose notes, tonal center, key signature, chord root, and slash bass. |
| E-flat alto | **`+9 chromatic semitones`, `+5 diatonic steps`** | `chromatic=-9`, `diatonic=-5`, no octave change | Write a major sixth above concert in `G2`; transpose the same pitch-bearing notation items. |

For tenor, the inverse separates the B-flat interval from the octave because MusicXML's `chromatic` value excludes octave displacement ([MusicXML chromatic](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/chromatic/); [MusicXML octave-change](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/octave-change/)). The renderer must transpose note spelling diatonically first and then derive the accidental, which keeps examples such as concert F major as written G major for tenor and D major for alto rather than accepting a MIDI-equivalent but incorrectly spelled key ([Yamaha](https://www.yamaha.com/en/musical_instrument_guide/saxophone/play/play003.html)). Transpose a chord symbol's root and slash bass as pitch classes but preserve its quality, alterations, extensions, additions, and omissions; the tenor octave does not appear in chord-symbol text.

## Data boundaries prevent profiles from changing phrases

**Cited project rule:** a core generation request consumes an explicit validated concert range and already-resolved register window, produces an immutable concert-pitch timeline, and contains no display transposition; notation then redraws that same timeline ([First-release specification](../../specs/first-release-master-spec.md); [Notation Display Preserves Phrase](../rule_notation_display_preserves_phrase.atom.md)). **Adopted implementation contract:** outer session intent may retain the player choice `Varying`, while every candidate core request has one resolved window. Profile data owns `id`, `concertRange`, and versioned register-window parameters; planners receive the resolved range/window and never branch on `profile.id`; notation receives the immutable timeline plus display convention and never reads profile range to alter pitches. Range validation requires integer endpoints, `minMidi < maxMidi`, a span of at least 24 semitones, recognized policy version, windows contained in the active range, and intersecting adjacent windows ([Instrument Profile](../entity_instrument_profile.atom.md)).

### Extending the adopted profile collection

Add a supported planner-facing profile only as declarative data shaped as `id`, `concertRange: { minMidi, maxMidi }`, and `registerWindows: { algorithm: "overlapping-three-window-v1", minimumSpan: 12, widthNumerator: 1, widthDenominator: 2 }`. The extension checklist is: choose a stable profile ID; supply inclusive integer concert-MIDI endpoints where `minMidi < maxMidi` and `maxMidi - minMidi >= 24`; use that recognized policy and its exact parameters; derive its Low, Middle, and High windows, then validate that they are contained by the active range and that adjacent windows intersect; register the profile in the adopted profile collection; extend the closed TypeScript profile-ID union for the newly supported ID; and add literal endpoint and derived-window boundary tests. Never add profile-specific planner branches. Keep transposition, clef, and display metadata outside planner-facing profile data; they remain notation concerns.

The result preserves the four-measure contract at every boundary: a selected profile and resolved window are hard constraints on all source events, while display transformation changes no duration, measure, event ordering, concert MIDI value, harmony, seed, selected profile, or range policy. Determinism also requires a named register-resolution stream separate from melody planning, fixed candidate order `Low, Middle, High`, and persisted requested/resolved register and window data; presentation changes must never enter either seed derivation ([Seeded Phrase Reproduction](../rule_seeded_phrase_reproduction.atom.md); [Register-window research](Saxophone%20profile%20ranges/register-windows.md)). The governing range atom now records the adopted profile policy, so no obsolete hard range reaches profile consumers.

**Adopted post-generation instrument-profile switching:** validate unchanged concert events against both the new profile's active range and the resolved whole-phrase window required by the current Register selection. Low/Middle/High use the corresponding new-profile window. For Varying retention, derive the same canonical window identities/register-stream keys from the existing seed, resolve one candidate before validation, and validate the existing phrase against it; do not run generation feasibility merely to retain a phrase. Retain and redraw only when every event fits both constraints. Otherwise retain controls, select a fresh seed, and regenerate, at which point Step 7 evaluates complete-phrase eligibility under the new profile and selects among successful windows. Never transpose source events to fit. This remains independent of display-mode selection. Later widening for skill, style, or player-selected variants requires a new declarative profile-data decision and player audition, not a relaxed generator constraint.

## Conclusion

Adopting the two saxophone profiles now turns a deferred range question into a small, testable data decision: the generator receives `46-70` or `51-75`, derives the corresponding fixed windows, and has no reason to know which saxophone it serves. The common written C4-C6 target is the key product simplification: it makes the default vocabulary familiar to both saxophonists without sacrificing concert-pitch determinism or forcing a false common sounding range.

The stronger architectural result is that an alto phrase can be displayed in B-flat notation, a keyboard phrase can be displayed in E-flat notation, and every one remains exactly the same four-measure concert phrase. That decoupling prevents display preferences from becoming hidden playability or generation settings, while leaving future physical-range expansion available for deliberate, separately tested decisions.
