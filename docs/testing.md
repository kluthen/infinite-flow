# Testing

This document records how Infinite Flow is tested: the test layers and where a new test goes, the
npm scripts that run them, the two browser harnesses and the seams a test drives them through, the
rules that keep every run deterministic, and the list of test fixtures. Each chunk of work that adds
a layer, a script, a harness seam, a fake or a fixture updates this document in the same change.

### Where a new test goes

- **Pure logic** (no DOM, no browser API) gets a Vitest spec under `tests/unit/`, at the path that
  mirrors its source file: `src/domain/rhythm/syncopation.ts` is tested by
  `tests/unit/domain/rhythm/syncopation.spec.ts`. A component or composable spec goes under
  `tests/unit/components/` or `tests/unit/composables/` the same way. A session engine or runner
  spec goes under `tests/unit/session/`, next to `session-harness.ts` (see
  [The session driver](#the-session-driver)).
- **Behaviour on screen** gets a Playwright spec. Use the production preview (`tests/e2e/workspace/`)
  when the real app can reach the state on its own, and the workspace harness (`tests/e2e/release/`
  today) when the test needs a fixed seed, a held generation or a forced failure.
- **Audio timing** gets a Playwright spec under `tests/e2e/audio/`, on the workspace harness's fake
  audio clock when the test checks exact times, and on its real audio clock (`?audio=real`) when
  it checks what the browser's own `AudioContext` does.
- **A practice session on screen** (starting, the cue row, the locks, the ends) gets a Playwright
  spec under `tests/e2e/session/`, on the workspace harness's fake audio clock, using
  `session-helpers.ts` (see [The session screen specs](#the-session-screen-specs)).
- **MIDI input** gets a Playwright spec under `tests/e2e/midi/`, on the workspace harness's fake
  MIDI access and fake audio clock, so every note is stamped at an exact audio time (see
  [Fake MIDI access](#fake-midi-access)).
- **The controller connection** (`controller-status`, the connection sheet, the check) gets a
  Playwright spec under `tests/e2e/controller/`, using `controller-helpers.ts` (see
  [Driving the connection sheet](#driving-the-connection-sheet)).
- **The last-session Review and its export** (what a session end leaves, `review-link`, the
  downloads) get a Playwright spec under `tests/e2e/review/`, on the workspace harness's fake audio
  clock, using `review-helpers.ts` (see [The Review specs](#the-review-specs)).
- **On-device storage** (the storage port, the database, its migrations, the record envelope, a
  store's codec, the save policy) gets a Vitest spec under `tests/unit/storage/`, in the Node environment, on a
  fresh in-memory IndexedDB from `storage-test-doubles.ts` (see
  [Fake IndexedDB and storage manager](#fake-indexeddb-and-storage-manager)). A kept-session codec
  spec needs no database and builds its sessions with `kept-session-fixtures.ts` (see
  [Kept-session fixtures](#kept-session-fixtures)).
- **Engraving and layout** of one phrase gets a spec under `tests/e2e/notation/`, driven through
  the notation harness.
- **A timing measurement** that asserts on its numbers, or runs long, gets its own spec and its
  own `measure:*` script, and stays out of `test:e2e`. A correctness spec may log a reference
  figure on the side, never asserted, and stay in `test:e2e`: `review-long.spec.ts` does (see
  [The Review specs](#the-review-specs)).

`npm run quality` runs, and stops at the first failure: `format:check`, `lint`, `lint:links`,
`lint:health`, `test:unit`, `build`, `verify:boundaries`, `test:e2e`, `test:a11y`, `test:notation`,
`atd:lint`, `atd:check`. Run it on an idle machine. Several specs are timing-sensitive and time out
under CPU load, so never run it next to `atd audit` (which saturates the local model server), a
measurement script, or another test run.

`test:unit` needs `xmllint` (from libxml2; the Debian package is `libxml2-utils`) on the `PATH`:
`tests/unit/export/musicxml/musicxml-schema.spec.ts` runs it to validate the MusicXML export
against the MusicXML 4.0 schema, offline. The development container installs it. Without it that
spec fails; it never skips.

Every Playwright command starts all three `webServer` entries of `playwright.config.ts`, whatever
spec it runs:

| Port | Serves                                                                                          | Built by                                                       |
| ---- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 4173 | The production build (`dist/`) through `npm run preview`. It is Playwright's default `baseURL`. | Nobody: run `npm run build` first. `quality` builds before it. |
| 4174 | The notation harness (`dist-notation-harness/`).                                                | `npm run build:notation-harness`, as part of starting.         |
| 4175 | The workspace harness (`dist-workspace-harness/`).                                              | `npm run build:workspace-harness`, as part of starting.        |

None of the three reuses a running server, so a dev server or preview already bound to one of these
ports makes the run fail.

## The workspace harness

**Files.** `tests/e2e/workspace-harness/index.html` and `main.ts`, the engraver seam
`tests/e2e/workspace-harness/vexflow-engraver-loader-seam.ts`, the audio seams
`tests/e2e/workspace-harness/audio-seams.ts`, the MIDI seams
`tests/e2e/workspace-harness/midi-seams.ts`, the session browser seams
`tests/e2e/workspace-harness/session-browser-seams.ts`, the session controller seam
`tests/e2e/workspace-harness/session-controller-seams.ts`, the session runner seam
`tests/e2e/workspace-harness/session-runner-seam.ts`, the export seam
`tests/e2e/workspace-harness/export-loader-seam.ts`, the saved-data seams
`tests/e2e/workspace-harness/storage-seams.ts`, the typed API
`tests/e2e/workspace-harness-window.d.ts`, and the build config `vite.workspace-harness.config.ts`.
It is served on port 4175 and has no PWA plugin and no service worker.

**What is real.** The harness mounts the production `App.vue` tree with the production styles. Its
workspace session is built by `composeWorkspaceSession` and handed to `App.vue` through the
`WORKSPACE_SESSION_FACTORY` provide/inject point. Generation runs in the real Worker through the
real client, and notation is engraved by the real VexFlow adapter. The audio transport is the real
`createAudioTransport`, on the fake audio clock and output by default or on the real Web Audio
output with `?audio=real` (see [Audio modes](#audio-modes)). The MIDI controller is the real
`createMidiController`, on the fake MIDI access by default or on the browser's own Web MIDI with
`?midi=real` (see [MIDI modes](#midi-modes)). The window shape the session judges is the real
probe adapter, moved with `page.setViewportSize`, and so is the page activation, which a spec's
real click, tap or key press makes (a script's `click()` fires no input event and does not), and
the page leaving, which a real reload or a dispatched `pagehide` marks and a dispatched `pageshow`
with `persisted` true clears; the wake lock, the orientation lock and the page visibility are
fakes (the fake page does not hide on a real `pagehide`, so a spec that cuts a session short hides
it from a `pagehide` listener of its own, and shows it again itself; see
[Fake session browser ports](#fake-session-browser-ports)). Only
randomness, timing and fault injection are replaced, plus the length of the history the Review
reads, for the long-Review specs. Nothing in `src/` knows the harness exists: the seams are injected
dependencies, plus three Vite aliases (the engraver loader, the export loader and the workspace's
session runner module, which the controller's chunk imports by its `@/` path).

phrase still generates with its queued seed either way. The production specs can load the page
with a query string too: `gotoWorkspace(page, search?)` in `tests/e2e/workspace/helpers.ts` (for
example `gotoWorkspace(page, '?prewarm=off')`, which the browser latency spec uses in its `off`
mode).

**Pre-generation in the harness.** The harness reads the Idle pre-generation policy from its page
URL with its own default: with no `pregeneration` parameter it is `disabled`, unlike production,
so no spec meets a background attempt unless it asks for one. `?pregeneration=on` enables it
(`off` disables it, and a mistyped value throws, through production's own parser). Built with
`VITE_HARNESS_PREGENERATION=on`, the harness's default is `enabled` instead (`off` or no value
keeps it `disabled`; any other value throws): the `test:e2e:pregeneration` lane runs the whole
`test:e2e` list that way, so every journey also passes with background attempts running. A spec
that needs pre-generation off whatever the build loads `?pregeneration=off` explicitly.
`tests/e2e/workspace/pregeneration.spec.ts` loads it that way through
`gotoPregenerationHarness(page)` in `tests/e2e/workspace/pregeneration-helpers.ts`, whose other
helpers read the call records (`generationRecords`, `backgroundRecordsFrom`,
`playerOrSessionRecordsFrom`), hold and release the background gate (`holdBackground`,
`releaseBackground`, `untilBackgroundHeld`), wait for a full queue (`untilQueueFull`, four
phrases: `QUEUE_SIZE`) and compute the plan's seeds and phrases (`rungSeeds`, `phraseOfSeed`,
`readyWithSessionSeed`). Its cases: a session spends the ready phrases instead of requesting
them, a regeneration and Start each cancel a held attempt and never wait for it, a change of the
queue's key discards the ready phrases while a tempo change keeps them, a window crossing that
steps the density down discards the phrases made at the wider density, nothing runs while a
Review shows, and nothing is written to storage.

### Audio modes

The URL chooses where the harness's audio transport runs. Any other `audio` value throws.

- **Fake** (the default, or `?audio=fake`): the transport runs on `createFakeAudioRig()` (see
  [Fake audio clock and output](#fake-audio-clock-and-output)). Its clock starts at 0 and moves
  only when a spec calls `audio.advance`, so every time is exact and a run repeats exactly. No
  `AudioContext` is ever created. The session controller's wake-up timer is an extra timer of the
  same rig, so `audio.advance` drives the session screen too.
- **Real** (`?audio=real`): the transport runs on the production seams, `openWebAudioOutput` and the
  wake-up Worker timer, with the output wrapped by the same recorder the fake uses. The first Start
  audio click creates the page's one `AudioContext`, and time is the real audio clock. Headless
  Chromium runs it with no launch flag: the Playwright click is a real user activation, so the
  context runs and `currentTime` advances.

### MIDI modes

The URL also chooses where the harness's MIDI access comes from. Any other `midi` value throws. In
every mode the controller is the production `createMidiController`, reading the harness audio
transport's `clockAnchor()` once the audio is unlocked (no clock before, as in the app, so a note
played before then is dropped unless it is the starting note after the page's first click), with
every state change and note it reports recorded for
`stateLog`, `playedNotes` and `endedNotes`.

- **Fake** (the default, or `?midi=fake`): the controller runs on `createFakeMidiAccess()` (see
  [Fake MIDI access](#fake-midi-access)), with no device plugged in. A spec plugs devices and
  plays notes through the `midi` seams. Each message is stamped at the audio time the spec gives,
  through the fake audio clock's `performanceTimeAt`, so these controls need the fake audio clock
  too and throw with `?audio=real`. The fake browser's state at load comes from the URL, so a
  reload keeps it as a browser does: `?midiPermission=granted|prompt|denied` sets the permission
  it reports, and `?midiDevices=` (a JSON array of `{ id, name, manufacturer }`) plugs those
  devices in before the app loads. The remembered-controller specs use them
  (`gotoControllerHarness`'s `atLoad`).
- **Unsupported** (`?midi=unsupported`): the same fake, built as a browser without Web MIDI. The
  controller starts `unsupported` and asks for nothing.
- **Real** (`?midi=real`): the controller runs on `createWebMidiAccessProvider(navigator)`, the
  browser's own Web MIDI. The fake-only controls throw. Headless Chromium answers `denied` even
  with the `midi` permission granted, so this mode can only check that the answer is a typed
  state.

**The engraver loader seam.** `vite.workspace-harness.config.ts` aliases

A spec that needs saved data opens the harness (its browser context starts empty), seeds through
`storage.seedSettings` (and `storage.seedMyInstrument` for my instrument), then reloads the page,
so the next load reads what was seeded. With `?storageLoad=held` the load does not start until
`window.__workspaceHarnessHeldLoad.release()`, which the page publishes at once: until then the
page shows only its background. With
`?storageRead=fail` every read of the app's port fails, and with `?storageRead=slow` each ends a
second after the start-up wait, so the visit starts from the defaults. The app's port is the opened
port wrapped by these injections (the keyed read included); the seeds, `storage.records` and
`storage.keyedRecords` bypass them. With `?storageRefuse=quota|other` the app's port refuses every
change from the load on, as `storage.refuseSaves` would, so the load's clean-up of damaged
sessions meets the refusal. The specs are in
`tests/e2e/storage/`; their shared helpers (`storage-helpers.ts`) also record the controls at the
workspace's first draw, before the browser paints it, through a `MutationObserver` an init script

`your-data.spec.ts` and `your-data-deletions.spec.ts` (helpers in `your-data-helpers.ts`) drive
the Your data sheet through its
three openers; an init script stubs `navigator.storage.estimate()` (its `usageDetails.indexedDB`

The `session-midi-*.spec.ts` specs (chunk 17) drive the controller inside a session on the fake

`silence-timeout` and `controller-lost`. `session-midi-helpers.ts` holds their steps:
`connectDevice(page, device)` (plug the device in, then the harness's `midi.connect` and
`midi.select`: connected with no sheet and no check), `noteOn`, `noteOff` and `tap` (a note at an
audio time, now by default), `unplugNow` and `plugIn`, `midiKind`, `expectedNotesOf(timeline,
phraseNumber, startAt)` (a phrase's expected notes on the audio clock, read from its concert

`disconnectBanner`, `ackedNoteIds` (the `data-note-id` of every staff glyph with `note-ack`),
`noteKey`, `expectStillRunning`, `expectEndedBetween(page, cause, from, to)` (ended on its own while

**A note is played at an audio time.** `midi.noteOn`'s time is converted to the fake
`performance.now()` timeline and back by the controller, so a note stamped at the clock's time now
(or at an expected note's onset, once `clockTo` has moved there) lands exactly there. A note at
Idle needs the audio unlocked, which `midi.connect` does; a port the page never opened delivers
nothing, as in a browser (the fake throws). A look-ahead phrase's notes come from
`generatedTimelines()`: the first answer after the session's start is phrase 2 when its first
attempt is accepted, and the closed history's `timeline` confirms it.

**Driving silence and a loss on the fake clock.** The silence rule and the loss countdown run on
the session's audio-time agenda, which `audio.advance` steps every 25 ms. To prove "more than
30 s", move the clock to 29.9 s and exactly 30 s after the last note (still running), then to
30.1 s (ended `silence-timeout`, its fade scheduled in (30, 30.1]). A loss is `midi.unplug` at the
clock's time: the banner reads 30 s at once and one second less per second; `midi.plug` of the same
device inside the window reattaches it (a different device is ignored); with no replug the session
ends `controller-lost` with its fade scheduled within 50 ms after 30 s. The silence rule is
suspended while the device is away and counts again from the reattachment.

**Screenshot equality.** Item 7's proof that a wrong note changes nothing on screen compares PNG
buffers byte for byte. The window is fixed at 1280 × 800 with a seeded phrase; phrase 2 is readied
and drawn first, so nothing on the staff is still due to change; the fake clock is not moved
between the shots, so the playhead band stays put; and `workspaceShot` waits for the fonts, for
every animation to stop and for two frames before each `page.screenshot`. The shots before and
after each wrong note must be `Buffer.equals`; as a control, the matched note's shot must differ.

`tests/e2e/controller/` drives the header's `controller-status` and the connection sheet (see

audio clock and the fake MIDI access. Every sheet is reached through real clicks and keys, as the
player reaches it: the `controller-status` click must be a real Playwright click, since it is the
page's audio-unlock click. The `midi` seams only set the scene:

- **Devices.** `midi.plug` before the click gives No device found (none), the check (one) or the
  picker (two or more); `midi.plug` and `midi.unplug` while the sheet is open drive its device
  changes.
- **The request.** `midi.denyNextRequest` gives Permission denied and the MIDI-blocked badge.
  `midi.holdNextRequest` keeps the request in flight, so the spec can read Requesting access, close
  the sheet while the browser "asks", and settle it later with `midi.releaseHeldRequest` (a late
  "allow" or, after `denyNextRequest`, a late "block"). `midi.requestCount` proves that a click
  asked nothing.

  shows Waiting for your browser. `midi.setPermission('granted')` (or `denied`, or `unknown`)
  before the click shows Checking instead.

## The notation harness

**Files.** `tests/e2e/notation-harness/index.html`, `main.ts` and `fixtures.ts`, the typed state
`tests/e2e/notation-harness-window.d.ts`, and the build config `vite.notation-harness.config.ts`. It
is served on port 4174; every notation spec sets `test.use({ baseURL: 'http://127.0.0.1:4174' })`.
It mounts `PhraseScore` without the app shell, inside a real `staff-frame` in the `#app` container,
with the app's own stylesheet (Tailwind runs in the harness build), because the notation layout
reads its height budget from `staff-frame`'s computed `max-block-size`.

**URL parameters.** A missing required parameter throws; only the optional ones below have defaults.

- `width` (required): the frame's outer width in CSS pixels.
- `source`: `fixture` (the default), `generated`, or `empty`, which mounts `PhraseScore` with no
  phrase at all, as the workspace does before its first phrase.
- With `source=fixture`: `fixture`, one of the named fixtures listed below.
- With `source=generated`: `seed`, `tonal`, `collection`, `density`, `variety`, `syncopation`,
  `silence`, `register` and `profile`, each validated against the domain catalogs, and optionally
  `contour` (default Arch), `leapiness` (default Shaped) and `chaos`, the arpeggio chaos (default
  Predictable), which the calibration sweep varies. The other controls are fixed (tempo 90, Gentle
  diatonic motion, Settled tension, Neutral musical profile). The phrase is generated on the
  page's main thread with `generatePhrase`, and engraved in the chosen instrument's written pitch. A
  generation failure throws as a page error; no state is published for it.
- With `source=generated`, a player-made instrument instead of `profile` (which must then be
  absent): `myLow` and `myHigh`, its written range as MIDI notes, and optionally `myOctaves` and
  `mySemitones` (default 0) and `myDirection` (`lower`, `same` or `higher`; default `same`), its
  transposition, and `myClef` (`treble` or `bass`; default `treble`), its clef. The harness builds
  it with the real `makeMyInstrument` on the C MIDI keyboard template (named "Harness
  instrument"), the controls name `my-instrument` and its profile goes to `createGenerationIntent`
  as data; the clef stays out of the intent, and the written phrase carries it, so the phrase is
  drawn in that clef. The staff is drawn at the shared system-position size
  `planSystemPositionUnits` gives its written range in its clef. An invalid instrument, or a
  `myClef` other than `treble` or `bass`, throws.
- `savedRange` (optional, any source): `<low>-<high>`, a saved my instrument's written range as MIDI
  notes, read in `savedClef` (`treble` or `bass`; default `treble`). The staff is drawn at the
  shared size they give, while the phrase's own instrument (a built-in, or a fixture's) is engraved
  in its own clef. It cannot be combined with a player-made instrument, and `savedClef` without
  `savedRange` throws. Without either, `PhraseScore` gets no size and draws the built-in 160 units.
- `phrase` (optional, default 1): the phrase number `PhraseScore` engraves the phrase as, which
  every note identity on the score carries. The default is phrase 1, the phrase a session starts
  with.
- `theme` (optional): `light` or `dark` sets the page root's `data-theme` as the app's theme control
  does; absent, the page follows the system colour scheme. Any other value throws.

**Published state.** `window.__notationHarness` follows `PhraseScore`'s lifecycle:

- `{ state: 'pending' }` until the first engraving settles;
- `{ state: 'ready', engraved: { staffSpacePx, widthPx, heightPx, requiredUnits, systemCount,
positionBlockPx } }`, where `positionBlockPx` is the height of one reserved system position;
- `{ state: 'error', errorCode, errorDetails }`, for example `notation_no_room` (the window has no
  room for the staff) or `notation_notes_too_wide` (this phrase's notes don't fit).

Every ready state also carries `clef`, the clef the engraved phrase carries and is drawn in
(`treble` for a built-in and a fixture, the player-made instrument's `myClef` otherwise),
`systemPositionUnits`, the shared size it was engraved with (160 unless the URL names a player-made
instrument or `savedRange`), and `staffTopLineUnits`, the staff's top line placed in it by
`planStaffPlacement` for the phrase's written range in its clef.

Every state also carries `engraveCount`, the number of successful engravings since the page loaded,
so a spec can prove that something (a browser toolbar showing or hiding) caused no redraw. Every
ready state also carries `layoutInputsBeforeEngrave`, how many `layout-inputs` reports
`PhraseScore` had made when it reported that engraving. A spec
that resets the state to `pending` drops it until the next publish.

Every ready state also carries the note identities and the overlay seam:

## Fake audio clock and output

The audio transport takes its audio output and its wake-up timer through injected seams
(`src/audio/audio-ports.ts`). Unit tests replace both with `createFakeAudioRig(options?)` from
`tests/unit/audio/fake-audio.ts`, which never touches Web Audio or a Worker and imports no Node
module, so the workspace harness reuses it:

- **The clock** starts at `startTime` (0 by default) and moves only on `advance(seconds)` or
  `advanceTo(t)`. It steps on the grid `startTime + k * 0.025` and wakes the fake timer after
  every 25 ms step, as the Worker timer would, so the look-ahead scheduler plans sound exactly as
  it does in the browser, and long runs do not drift.
- **The output** records every call as a `FakeAudioEvent`: `click` (bus, time, accent, route),
  `backing` (bus, voice `bass` or `chord`, MIDI pitch, start `at`, end `until`), `gain` (gain
  stage, value, time), `fade` (bus, time, duration) and `open-bus`, each stamped with
  `scheduledAt`, the clock's time at the call. `events()` returns them in order, `clicks()` the
  clicks alone and `backingNotes()` the backing notes alone.
- **What is heard.** `audibleClicks()` returns the clicks that sound, with the click-volume gain
  they sound at: the volume is above zero, the click is enabled or on the count-in route, and its
  bus has not started fading. `audibleBacking()` does the same for the backing notes: the backing
  on/off gain and the backing volume are both above zero at the note's start, and its bus has not
  started fading. Both read the gains at a sound's start only. `gainAt(gain, t)` reads one gain at
  a time.
- **Shared with the real output.** `recordAudioOutput(output)` is the recorder the rig itself uses,
  and `audibleClicksOf(events)` and `audibleBackingOf(events)` are the readings behind
  `audibleClicks()` and `audibleBacking()`. The harness's `?audio=real` mode wraps the real Web
  Audio output with the same recorder, so both modes give the same event shape and the same
  audible readings.
- **A fake `performance.now()` timeline.** The rig's output answers `anchor()` with the clock's
  time and a fake `performance.now()` time running `performanceOffsetMs` ahead of it
  (`FAKE_PERFORMANCE_OFFSET_MS`, 50 000 ms, by default: far from zero, so a test that forgets to
  map a MIDI timestamp fails). `performanceTimeAt(t)` gives the `performance.now()` time of audio
  time `t`, so a fake MIDI message stamped with it maps back onto exactly `t`.
- **Extra wake-up timers.** `createExtraWakeTimer()` returns a further fake timer on the same
  clock, a new one per call, woken right after the transport's timer on every step; `running()`
  says whether it is started. The session controller takes its own wake-up timer this way (its
  `sessionClock.createWakeTimer` seam), so one `advance` drives the transport and the session
  screen's count-in, phrase starts and deadlines together.

`tests/unit/audio/audio-transport.spec.ts`:

```ts
const harmony = await queueBacking(page, 1) // returns the harmony it queued

const notes = await backingNotes(page) // each on a click, none before countInEndsAt
```

## Fake MIDI access

The MIDI controller takes its Web MIDI access through an injected `MidiAccessProvider`
(`src/midi/midi-access-port.ts`, see [`docs/midi-input.md`](midi-input.md#the-ports)). Unit tests
replace it with `createFakeMidiAccess(options?)` from `tests/unit/midi/fake-midi-access.ts`, which
imports no Node module and no test framework, so the workspace harness reuses it. It behaves like
Chromium where the controller depends on it:

- **Devices.** `plug(device, timestampMs?)` plugs a device in; a known id comes back as the same
  port object, and a port that was open reopens itself (unless `reopensOnReplug: false`, which
  leaves it for the controller to reopen). `unplug(id, timestampMs)` takes it out.
- **Notes.** `noteOn(id, pitch, velocity, timestampMs, channel?)`, `noteOff(…)` and
  `send(id, bytes, timestampMs)` deliver a message from an open, present device; sending from any
  other throws, as a real port delivers nothing then.
- **The request.** Requests resolve `granted` unless `denyNextRequest()`, `failNextRequest(error)`
  or `holdNextRequest()` (settled by `releaseHeldRequest()`) says otherwise; `supported: false`
  builds a browser without Web MIDI.
- **The permission.** `permission()` answers like a browser's permission query: `prompt` until a
  request is answered (`unknown` without Web MIDI), then `granted` or `denied` as answered.
  `setPermission(state)` sets it, for the sheet's Checking and Waiting sub-states.
- **Opening.** `holdNextOpen(id)` keeps the next `open()` in flight until `releaseHeldOpen(id)`.
- **Queries.** `requestCount()`, `openCount(id)`, `isListening(id)` and `connectionOf(id)`.

Timestamps are `performance.now()` milliseconds. A test takes them from the fake audio rig's
`performanceTimeAt(t)` (see [Fake audio clock and output](#fake-audio-clock-and-output)), so a note
stamped there lands at exactly audio time `t`. `tests/unit/midi/midi-controller-rig.ts` wires both:
`createControllerRig(options?)` plugs the given devices, builds the controller on the fake access
and the rig's anchor, records every change and note, and gives `at(t)`. Condensed from
`tests/unit/midi/midi-controller-lost.spec.ts`:

```ts

// notes ends with { kind: 'ended', note: { pitch: C4, velocity: 90, onsetAt: 1, releaseAt: 2.25 } }
midi.plug(KEYS_A, at(4)) // the same port: connected again, with no new request
```

A harness spec does the same through `window.__workspaceHarness.midi`, giving audio times
directly: the harness stamps them through the fake audio clock. Condensed from
`tests/e2e/midi/midi-input.spec.ts`:

```ts

await connectMidi(page) // unlocks the audio, then connects
```

## Fake IndexedDB and storage manager

The storage port (`src/storage/storage-port.ts`, see [On-device storage](storage.md)) takes its
IndexedDB factory and storage manager as options, so its unit specs under `tests/unit/storage/`
run on stand-ins and never on a browser. They run in the Node environment
(`// @vitest-environment node`).

IndexedDB comes from the `fake-indexeddb` dev dependency. Each test builds a fresh, empty
in-memory database with `freshFactory()` (a new `IDBFactory` from `fake-indexeddb`) and passes it
to `openStoragePort({ factory, appVersion })`. The global shim (`fake-indexeddb/auto`) is never
loaded, so no test sees another's data and none depends on a global `indexedDB`. Two tabs are
two ports, or a port and a raw connection, opened on the same factory.

`tests/unit/storage/storage-test-doubles.ts` holds the rest:

- `TEST_APP_VERSION` (`3.0.0-test`) and `sampleRecord(payload, dataVersion?)`, a record with valid
  versions and a payload; `DATABASE`, the default database name.
- `syntheticStep(toVersion, ran?)`, a migration step that rewrites nothing and records in `ran`
  that it ran, and `migrationsUpTo(version)`, the production steps followed by synthetic steps up
  to `version`. A spec passes them through the port's `migrations` option to open the database at
  a higher data version (a synthetic step 1 → 2), as a newer app would; production code has no
  test-only branch for it.
- `withRawDatabase(factory, inspect, version?)` opens the database straight on the factory,
  without the port, runs `inspect` on that connection and closes it, so it never blocks a later
  upgrade. With `rawGet` and `rawPut` a spec inspects what is stored, or tampers with it as a
  newer tab would (for example raising `meta`'s data version without an upgrade).
  `databaseNames(factory)` lists the databases the factory holds, to prove a deletion.
- `failingPutFactory(makeFailure, path, real?)` wraps a factory so every `put` fails with the
  given `DOMException`, either thrown by the request call (`'request'`) or as the error of an
  aborted transaction (`'transaction'`), the two ways a browser out of space reports a
  `QuotaExceededError`. The wrapped factory is a fresh one unless `real` is given, so a spec can
  fill the database first and then prove a failed batch changed nothing. A batch puts into several
  stores, and each store's `put` fails. Everything else is the real fake database.
- `blockedOpenFactory()` gives a factory whose `open` throws a `SecurityError`, as a browser with
  storage blocked does, over a real fake factory (`real`) that still deletes databases: the port
  opens `unavailable`, and Delete everything still runs.
- `recordingManager()` gives a storage manager double that answers fixed values (an estimate of
  1200 bytes used of 50 MB, not persisted, persistence granted) and records each call by name in
  `calls`. A spec that leaves the manager out checks the insecure-context refusals.

`tests/unit/storage/save-policy-doubles.ts` holds what the save policy's specs add on top:

- `readyPort`, `filledPort`, `outdatedPort` and `unavailablePort` open a port in each of its states
  over a given factory; `openNewerTab` and `raiseMeta` act as a newer tab, by an upgrade or by
  raising `meta`'s data version without one.
- `refusingPort(real)` wraps a real port so its writes, deletes, batches and Delete everything are
  refused on demand: after `refuse(kind)`, each throws a `StorageError` of that kind. Reads and the
  storage manager calls go to the real port.
- `countCalls(port)` counts, from the moment it is called, every call to the port's data methods
  (`portCalls()`) and every transaction opened on the fake database (`transactions()`,
  `readwriteTransactions()`), to prove that nothing reaches the database during a session, or that
  a batch is one transaction.
- `recordFailures(policy)` and `recordStates(policy)` record what the policy reports and the states
  it turns to; `protectedManager()` is a recording manager whose data is already persistent;
  `lackOfSpace()` and `diskFailure()` give the two failures; `settled(promise)` captures how a
  promise settles.

The saves of the player's settings have their own stand-ins: `recordingPolicy()`
(`tests/unit/storage/recording-save-policy.ts`) is a `SavePolicy` that records the calls the
settings saver makes, the changes to kept sessions included (its saving state stays `on`; any
other member throws "not used"), and `recordingSaveSettings()` with
`provideSaveSettings()` (`tests/unit/components/workspace/recording-save-settings.ts`) records the
saves a component makes and gives the `global.provide` entry for `SAVE_SETTINGS`, which every
mount of `WorkspaceShell`, `ScorePanel`, `SessionCueRow`, `MixControls` and `MixVolumeButton`
needs, since those inject the saver at setup and throw without it.

`__APP_VERSION__` is defined in `vitest.config.ts` through `scripts/app-version-define.mjs`, as
in the app's build, so `src/storage/app-version.ts` loads in unit tests and `app-version.spec.ts`
checks it against `package.json`.

## The session driver

`tests/unit/session/session-harness.ts` holds the shared builders of the session engine specs. It
drives the real `createSessionEngine` and replaces only its two seams:

- **Queued seeds.** `queuedProviders(firstSeed?, queueLength?)` hands out seeds `firstSeed`,
  `firstSeed + 1`, ... and request ids `session-1`, `session-2`, ..., records every seed in
  `seedsHandedOut`, and throws once the queue is empty, so a run is deterministic and a test can
  check that each attempt got a fresh seed.
- **Fake viewport.** `fakeViewport(below)` is a window-width reading the test moves by hand
  (`viewport.below = true`); the engine reads it each time it builds a request.
- **Real phrases.** `phraseOneFor(settings, options?)` generates a real phrase 1 at Idle through
  `generatePhrase`, and `successFor(intent)` the real successful outcome of an intent the engine
  requested; both are cached, since generation is pure. `failureOutcome(code?)` is a real
  generation failure outcome. `sessionSettings(overrides?)` builds the chosen settings, and
  `withoutTempo(intent)` drops the tempo for comparing intents built at different tempos.
- **Timed event driving.** `SessionDriver` starts one engine (start time, settings, phrase 1,
  viewport and providers all have defaults) and logs every output it returns. Its methods send one
  timed event each: `countInOver(at)`, `sounding(at, phraseNumber)`, `tick(at)`, `end(at, cause?)`,
  and, for the latest request, `fail(at)`, `crash(at)`, `succeed(at)`, `fit(at, fits)` and
  `accept(at)` (a success that fits). `exhaust(at)` fails every remaining rung of the ladder.
  `all(kind)`, `requests(phraseNumber?)`, `lastRequest()` and `kinds(outputs)` read the log.
- **Fake display.** `fakeDisplay(onScreen?)` is the display reading (`SessionDisplayReading`) the
  test moves by hand (`display.onScreen = true`); it answers the same for every phrase and logs
  each phrase number it was asked about in `asked`. The driver's default is `fakeDisplay(false)`.
  `UNREAD_DISPLAY` is the display for a run that never sends a settings change, the only event
  that reads it: a read throws. The runner specs and `history-recording.ts` pass it.
- **Settings changes and mutations.** The `mutation` option sets `SessionStart.mutation`
  (`SETTINGS_MUTATION_OFF` by default, so every older spec runs with the flag off), and the driver
  keeps the whole start in `start`. `change(at, settings)` sends a `settings-change` event.
  `settle(at)` answers every attempt of the latest requested phrase with its real outcome
  (`realOutcomeFor(intent)`, cached by the intent's content), a success fitting, until the phrase
  is decided or its ladder runs out.
- **The multi-phrase tension arc.** The `multiPhraseTensionArc` option sets
  `SessionStart.multiPhraseTensionArc` (`false` by default, so every older spec runs with the arc
  off).
- **Ready phrases.** The `readyPhrases` option sets `SessionStart.readyPhrases` (absent by
  default, so every older spec runs with none). `withoutRequestIds(value)` copies a value with
  every `requestId` removed, for comparing phrases built from different request-id providers, as
  a session with and without pre-generation are. The pre-generation plan's own builders are in
  `pregeneration-harness.ts` (see [Unit fixtures](#unit-fixtures-goldens-and-manifests)).

`tests/unit/session/scripted-session.ts` runs whole sessions on `SessionDriver` for the
settings-change and mutation specs:

- **Fast tempo.** `fastDriver(options?)` starts a driver at 0 at `FAST_TEMPO` (240 BPM, so one
  measure is 1 s), with optional settings, mutation flag, viewport, display and phrase 1 density.
  `soundingAt(n)` is when phrase n starts sounding in such a session: phrase 2's deadline is 1 s,
  and phrase n + 1's is 3 s after phrase n starts.
- **Scripted run.** `driveSession(driver, lastSounding, failFirst?)` answers phrase 2 during the
  count-in, then each phrase n + 1 half a measure after phrase n starts sounding, through
  `settle`; a phrase still undecided at its deadline becomes a repeat. `failFirst(n)` fails the
  first attempt of the phrases it names.
- **Reading it back.** `settingsChanges(driver)` lists the `settings-changed` outputs, and
  `settingsFor(driver, request)` the settings in effect for a request, from the chosen settings
  and those outputs.

**Driving a mutation.** A spec turns the flag on with a seed, `{ kind: 'on', seed: makeSeed(n) }`,
as `fastDriver({ mutation })`, and runs the session with `driveSession`. Where mutations land
follows from the seed alone, so a spec states it with `mutationPhrase(seed, k)` rather than by
hand. What a mutation changes follows from the seed too, so a spec that needs a particular one
names the seeds that give it and checks that they do: seeds 16 and 46 step the key and 40 and 44
the collection in `session-replay.spec.ts`. `session-engine-mutation.spec.ts` checks the
landing phrases, the flag off, a mutation after a note-density step-down and a register mutation
from Varying; the pure engine has its own specs (`settings-mutation.spec.ts`,
`settings-mutation-scales.spec.ts`, `settings-mutation-cadence.spec.ts`).

**Driving a settings change.** A spec brings the session to the state it needs (phrase 3
requested, or decided), sets the fake display, and sends `change(at, settings)` at a time chosen
against the pending phrase's deadline: more than one measure before it, exactly one, or less.
`session-engine-settings-change.spec.ts` covers the three cases of the discard rule (nothing on
screen with a measure left, partly on screen, less than a measure left), and
`session-engine-settings-carry-in.spec.ts` the carry-in of the phrase requested after the change;
both bring their sessions to that state with `settings-change-session.ts`.
`carry-in-adaptation.spec.ts` tests `adaptCarryIn` on its own,
and `carry-in-null-harmony.spec.ts` the generator's side of a carry-in without its harmony.
`workspace-session-runner.spec.ts` checks that the workspace's runner turns the player's choice
into the flag (its seed drawn first, none when off) and reads the display it is given.
`workspace-session-controller-vary-settings.spec.ts` drives the same rules through the session
controller over real runners: the flag, the settings the controls show, every way a session ends
(Stop, each shared end, a session staff failure, the silence timeout and a controller away for
30 s) dropping them before the fresh phrase, the profile's customized marking back as the
player left it, and a settings change sent with the rig's `changeSettings` while the
next phrase is drawn (kept) or, in the split layout, not yet drawn (discarded and readied again).
`workspace-session-runner.spec.ts` also checks that the multi-phrase tension arc flag is passed
on, and `workspace-session-controller-tension-across-phrases.spec.ts` drives the page's
`Tension across phrases` flag through the controller: off at load, changed only outside a session,
carried by each session's start, every phrase requested at its step while `shownSettings` keeps
the player's tension.

**Driving the tension arc.** A spec builds a `SessionDriver` with `multiPhraseTensionArc: true`
and runs it with `driveSession`. `tension-arc-cycle.spec.ts` tests the pure cycle: the step of each
phrase number, the clamping at Settled and Edge, and the settings a phrase is generated under (the
same object when nothing steps, a frozen copy otherwise). `session-engine-tension-arc.spec.ts`
checks, for each chosen tension arc, that the arc off gives the session without the flag and the
arc on steps each phrase by its number with no `settings-changed`. It also checks that a settings
change reports the tension arc as set, never stepped, while the phrases requested after it step
around the new settings, and that a flag that is not a boolean throws at start.
`session-engine-tension-arc-generation.spec.ts` runs both flags together over 40 mutation seeds
(each phrase steps around the tension arc then in effect, and the same seeds give deep-equal
logs), checks that the arc alone, the mutation flag off, also gives deep-equal logs for the same
seeds, round-trips stepped phrases through their replay keys, and property-tests the joins (see
[Determinism](#determinism)).

`tests/unit/session/history-recording.ts` holds the shared builders of the session history
reproduction and export specs. Unlike `SessionDriver`, it runs whole sessions through the real
runner:

- **Recorded sessions.** `recordRunnerSession(options)` runs one session through the real
  `createSessionRunner`, with the real `generatePhrase` as its `generate` seam and a `checkFit`
  that always passes, and records every output into a real history. Each phrase starts sounding
  one phrase after the one before, every generation answers at once (so no deadline passes and no
  repeat is decided), and the session stops once `phraseCount` phrases have sounded. Every stored
  intent is then the one the engine built, carry-in included. A runner error fails the test. The
  history records every phrase in `options.clef`, treble (every built-in's) by default.
- **Session inputs.** `settingsForCell(cell)` builds the settings of one seed-matrix cell, and
  `idlePhraseOne(settings, seed, noteDensity?)` a real phrase 1 generated at Idle.
- **Regeneration.** `regenerate(record)` generates a record's phrase again from its stored intent.
  `regeneratedMusicXml` and `regeneratedMidi` encode regenerated phrases without the history's
  export adapter, for a byte comparison with what the adapter hands the encoders.

`tests/unit/session/my-instrument-session.ts` builds sessions played with my instrument for the
history, kept-session, export and review specs: `lowHorn(clef)`, my instrument written C2 to C5
and sounding a minor third lower, in the clef given (both clefs give the same profile, since the
clef is display only); `myInstrumentSettings(instrument)` and `myInstrumentPhraseOne(settings)`,
its profile carried as data; and `recordedMyInstrumentSession(instrument, phraseCount)`, a
`recordRunnerSession` whose history records every phrase in the instrument's clef.

One unit test carries a time budget: "a long session" in `session-history.spec.ts` builds and
reads back a history of 2 000 phrases (about 2 h 15 min at 60 BPM) and fails above 250 ms. Unlike
the measurement specs, it is a pass/fail check inside `test:unit`. The budget is about a hundred
times the measured time, so a busy machine does not fail it. The measured figure is recorded in
[A long session](session-engine.md#a-long-session).

## Determinism

- **Same seed, same result.** Generation is a pure function of its intent, seed included. A test
  that needs a known phrase fixes the seed: `queueSeeds` in the workspace harness, the `seed`
  parameter in the notation harness, `makeSeed(n)` in a unit test.
  `tests/e2e/release/deterministic-replay.spec.ts` checks it end to end: seed 4242 generated twice,
  across a page reload, gives the same timeline, and seed 4243 gives a different one.
- **Injected clock.** Code never reads the time directly. It takes it from an injected clock that a
  test can replace, so a timing rule is tested by advancing the fake clock, not by waiting.
- **Timed events, no clock.** The session engine never reads a clock at all: every event carries
  its audio time. Its specs under `tests/unit/session/` drive it with a scripted list of timed
  events through `SessionDriver`, so deadlines, late results and repeats are tested by the times
  written in the test, with no waiting and no fake clock.
- **Tempo only sets the times.** `session-timing.spec.ts` runs the same event script scaled to 60,
  120 and 240 BPM and checks that the request intents are identical once `controls.tempo` is left
  out, with the same phrase numbers, steps and retries.
- **No test-only branches.** Production code carries no `if (test)` path. A test replaces a
  dependency through a seam that production code already exposes: `composeWorkspaceSession`'s
  providers, `viewport` width provider, `generate` function, `audio` transport and `midi`
  controller, the `WORKSPACE_SESSION_FACTORY` injection point, a fake `GenerationWorkerPort`, the
  audio transport's `openOutput` and `createWakeTimer`, the MIDI controller's access `provider`
  and `clock`, or a Vite alias in a harness build config.

- **The seed matrix with carry-in.** `tests/unit/domain/generation/carry-in/carry-in-matrix.ts`
  lists its 96 cells, in a fixed order: every instrument profile (3) × register choice (4) × four
  representative control sets × two seeds. It only lists the cells; each spec decides what to run
  and assert on them.
- **Joins are property-tested over the seed matrix.** `carry-in-join-matrix.spec.ts` chains six
  phrases for every cell: phrase 1 without carry-in, each later phrase with the carry-in of the one
  before, each with its own seed. Every join is re-validated, re-generated from its own request
  and seed, and checked to settle any leap recovery or tense note the phrase before left owing.
  The matrix must make every join and must contain both kinds of debt, so a change that stops
  phrases from ending owing, or stops the next phrase from settling it, fails there.
- **A recorded session reproduces over the seed matrix.** `session-history-reproduction.spec.ts`
  records a real session of five phrases for every cell through `recordRunnerSession`, so phrases
  2 to 5 carry in from the phrase before. Every record regenerates from its stored intent to the
  timeline it stored. For each of the three instrument templates, the recorded session encodes to
  the same MusicXML and MIDI bytes as the regenerated phrases.
- **A session replays from its inputs.** `session-replay.spec.ts` runs 50 fast sessions of ten
  phrases, mutation seeds 1 to 50, twice each from the same start and events, and checks the two
  logs are deep-equal. It runs each seed again with the first attempt of every third phrase
  failed: the logs differ, but the mutations (phrase, setting, from, to, settings) are the same,
  since they depend only on the start and the phrase numbers. A phrase requested after a key or
  collection mutation (its carried harmony dropped) round-trips through its replay key and
  replays to the same generation.
- **Joins stay valid across a tension-arc step.** `session-engine-tension-arc-generation.spec.ts`
  runs a seeded matrix of fast sessions of 12 phrases with the multi-phrase tension arc on: 8
  provider seeds × the 4 tension arcs × the mutation flag off and on. Every carried-in phrase
  passes the generation-result validation, join included. Across each step, a carried harmony kept
  fits the receiving intent, and one dropped with the key unchanged does not; the matrix must
  contain stepped joins, kept harmonies and dropped ones.
- **Every starting rhythm setting mutates to a supported one.** `settings-mutation.spec.ts` draws
  mutations from every unblocked combination of note density, rhythmic variety, silence density
  and syncopation, in each of the four window and step-down contexts, and checks that none lands
  on a blocked setting or on an unavailable Sixteenth.
- **Random cases from a fixed seed.** A property test over random inputs draws them from a seeded
  generator, so every run checks the same cases and a failure names the case to replay.
  `played-notes-midi-timing.spec.ts` draws 500 played sessions from mulberry32 seeded
  `0x1f2e3d4c`, and checks every onset against the file's own tempo map (see
  [Verifying the MIDI](export.md#verifying-the-midi)).

### Cold-generation goldens

`tests/unit/domain/generation/orchestration/cold-generation-golden/` holds four JSON goldens,
recorded once on the generator as it stood before the cold-generation speed-up (candidates
