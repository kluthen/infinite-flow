# Infinite Flow v2.0 release notes

Version 2.0.0, not yet tagged. Written on 2026-10-06.

## What v2.0 is

v2.0 turns the single-phrase generator of v1 into a practice session. Phrases roll on one after
another, each joined smoothly to the one before, over a backing, a click and a count-in. A MIDI
controller can start the session with its first note, and the notes played on time at the right
pitch light up. After a session, the Review shows what was played and exports it.

v2.0 is one release. It was planned as four, v2.0, v2.1, v2.2 and v2.4, and the product owner
folded them into one on 2026-10-05 (spec D183). The names stay as labels for parts of its scope,
as in the release-sequence table of
[master spec §11](../../specs/versions/v2/master-spec.md#release-sequence):

- **v2.0:** the core loop: rolling phrases, the backing, sessions, MIDI acknowledgement, the
  controller check, the Review and the export of the generated notes.
- **v2.1:** played notes shown in the Review and exported as their own MIDI file; the "Vary
  settings" flag, which changes settings during a session.
- **v2.2:** adaptive tempo ("Rising tempo") and the multi-phrase tension arc ("Tension across
  phrases").
- **v2.4:** the checks that need the reference hardware, the reference machine or a real program
  other than the browser.

## How to read the table

The table below is the release gate's evidence
([build plan chunk 21](../../specs/versions/v2/build-plan.md#chunk-21--v20-release-gate)). It
has one row per criterion of
[master spec §11](../../specs/versions/v2/master-spec.md#11-definition-of-done), in its order:
items 1 to 28, then the v2.1 criteria, the v2.2 criteria (each adaptive-tempo criterion of §10 and
each tension-arc criterion on its own row), then the v2.4 real-hardware checks. Items 6, 9 and 15
moved to v2.4 but keep their rows at their numbers. A criterion with parts that differ in status
has one row per part (9, 12, and the controller check).

- **Criterion:** the number and a short paraphrase. The spec's wording is the reference.
- **Evidence:** up to four tests, as `file` › 'test title'. A title with `%s`, `%i`, `$name` or
  `${...}` is a parameterized test, quoted as written in the source. A hand check points to where
  it is written down. The evidence named is a sample of the strongest tests, not every test.
- **Run by:** the npm script that runs the evidence.
- **Status:**
  - **Verified:** automated tests check it, and they pass.
  - **Hand check, done:** checked by hand or by a measurement script on the reference machine, on
    the date given.
  - **Hand check, after the tag (v2.0.x):** may follow the tag, as the spec allows; listed in
    [Hand checks after the tag](#hand-checks-after-the-tag-v20x).
  - **Not met:** the criterion does not hold as written.

## Gate commands

- `npm run quality` runs every automated gate, in order: `format:check`, `lint`, `lint:links`,
  `lint:health`, `test:unit`, `build`, `verify:boundaries`, `test:e2e`, `test:a11y`,
  `test:notation`, `atd:lint`, `atd:check`. Every **Verified** row rests on it. Run it on an
  idle machine, on the commit to be tagged. No timing constant was changed by the hardware
  tuning, so the automated tests already run with the shipped values.
- The measurement scripts below are not in `npm run quality`. The gate ran them on 2026-10-06 on
  the reference machine, and their results are written in
  [HARDWARE-CHECKLIST.md](../../HARDWARE-CHECKLIST.md) part E and
  [generation-latency.md](../generation-latency.md#2026-10-06-run-v20-gate):
  - `npm run measure:rolling`: the playhead against the heard audio, and the main thread during a
    240 BPM session (items 6 and 15);
  - `npm run measure:engraving`: the main thread while a phrase is engraved (items 1 and 15);
  - `npm run measure:latency:browser`: generation times in Chromium, the cold run after a
    setting change included (v2.4).
- `npm run measure:latency` (the same generation times in Node) was not needed for this gate.
- `npm run test:sweep` is the full item-1 sweep timed at real cost. It exists only on the
  unmerged branch `gate-sweep-density`, and it fails: see
  [Known issue: item 1](#known-issue-item-1).

## Known issue: item 1

Item 1 asks that, for every seed and every supported settings combination, at 60, 120 and
240 BPM, every phrase after the first is generated and engraved before its deadline. It is not met.

**How a session meets its deadlines.** During a session the app asks for each phrase ahead of time,
while the phrases before it play. Each phrase has a deadline: three measures after its request
(3 s at 240 BPM, 6 s at 120 BPM, 12 s at 60 BPM), and one measure for phrase 2. Generation runs
in one background worker, one attempt at a time. If an attempt fails, the failure ladder tries
again: the first attempt and three retries join the new phrase smoothly to the one before (the
carry-in), then one standalone retry does not. If no valid phrase exists at the deadline, the
phrase before is played again (a repeat). After two repeats in a row the app shows a non-blocking
"struggling" notice until a newly generated phrase starts sounding.

**What holds.** The tests below all run in `npm run quality`.

- The sweep's cases cover every supported rhythm setting, 284 of them, with seeds 7 and 13: 568
  cases. Every value of every other control, and both session flags, comes up at least once
  (`tests/unit/session/session-deadline-sweep-failures.spec.ts` › 'cover every supported rhythm
  setting with every seed, and every other value at least once').
- The failure ladder, on a slice of 24 of those cases at 60, 120 and 240 BPM, on the fake clock,
  each attempt costing a modelled 0.35 s on one worker. A failed attempt or a crashed request is
  recovered by the next carry-in retry; when every carry-in attempt fails, the standalone retry
  takes over; when every attempt fails, the phrase before repeats at the deadline, not earlier;
  two repeats in a row show the struggling notice until a generated phrase sounds. The session
  runs on to its planned end every time. Same file › 'recovers a failed attempt and a rejected
  request with the next carry-in retry at %i BPM', 'gives way to the standalone retry when every
  carry-in attempt fails at %i BPM', 'repeats phrase 1 at its deadline when every attempt of
  phrase 2 fails at %i BPM', 'shows the struggling notice at the second repeat in a row until a
  generated phrase sounds at %i BPM'.
- Deadlines fall on the measure grid at all three tempos, and the requests are the same at each
  tempo, tempo aside (`tests/unit/session/session-timing.spec.ts` › 'places every deadline on the
  measure grid at %i BPM', 'builds identical request intents at 60, 120 and 240 BPM, tempo
  aside').
- The struggling notice: `tests/unit/session/struggling-notice.spec.ts` › 'shows at the second
  repeat in a row, stays through a third, clears when a generated phrase sounds', 'never shows for
  a single repeat'; and in the real app, `tests/e2e/session/session-struggling.spec.ts` › 'shows
  from the second repeat in a row, stays through a third, and clears when a new carry-in phrase
  starts sounding', 'never blocks: the mix and Stop stay usable while it shows, and it goes with
  the end'.
- Engraving time comes from the hand measurement (HARDWARE-CHECKLIST.md part E): the longest
  main-thread block while engraving the densest phrase was 49.3–52.8 ms.

**What fails.** The full sweep was also run with each attempt timed at its real cost: the time the
real generator took for that request, in Node on the development machine, plus 0.1 s for the worker
round trip and the engraving, on one worker that keeps computing an attempt the session has given up
on. In 7 of the 568 cases, at least one phrase misses its deadline and is played as a repeat, and in
most of them several phrases in a row are. All seven are at Eighth or Sixteenth note density; every
Quarter case meets every deadline. The cause: in these cases a failed carry-in attempt runs for a
long time before it reports its failure, in most of them from about 6 up to 28 seconds, while
successful attempts take 280 ms at most. Such an attempt searches until it has tried every option or
used up its whole search allowance, and the failure ladder's three carry-in retries make the same
search again, with the same carry-in, each taking as long as the first. At 240 BPM, where the
deadline is 3 s away, even failed attempts of under a second each add up to too much. By then the
deadline has passed, and the worker is still busy when the next phrases are asked for. The session
keeps running and the struggling notice shows, so the ladder does its job, but the phrases are
repeats. The settings are deterministic, so a player who keeps such settings meets it every time.

The full sweep is the script `npm run test:sweep`
(`tests/sweep/session-deadline-sweep-{quarter,eighth,sixteenth}.spec.ts` › 'generates every
phrase after the first before its deadline, each attempt at its measured cost, at %i BPM'). It
runs for about 7 minutes, is not in `npm run quality`, and exists only on the unmerged branch
`gate-sweep-density`. The issue is tracked as ISS-009.

**Decision pending.** Whether v2.0 is tagged with this as a known limitation, or waits for a fix,
is the product owner's decision. It has not been made. Any fix changes the failure ladder's
settled behaviour, so it goes through the spec first.

## Reading notes

- **"Every seed and supported-settings combination" (item 1).** The full cross-product of the
  controls is about 212 million combinations per seed and per tempo, too many to run. It is read
  as every supported rhythm setting (284) × the seed matrix (seeds 7 and 13), with every value of
  every other control at least once. Tempo never reaches generation
  (`tests/unit/domain/generation/tempo-never-generation-input.spec.ts`), so the three tempos
  change only the clock.
- **Engraving within item 1** rests on the hand measurement (HARDWARE-CHECKLIST.md part E). The
  fake clock of the unit tests cannot time engraving.
- **Item 4's "nothing changes what is generated during a session"** holds with the Vary settings
  and Tension across phrases flags off, as they are at page load. With them on, the changes they
  make are governed by the v2.1 and v2.2 rows.
- **Item 6** is judged at the moment the playhead band's measure changes, not at the next painted
  frame, which comes one frame later by construction (spec D197).
- **Item 12's "in v2.0 only the generated-notes export action exists"** was written before v2.1
  was folded into v2.0. The played-notes export ships in v2.0: see rows v2.1-b to v2.1-g. The
  clause that no generated-notes file holds a played note still holds (rows 12b and v2.1-d).
- **Item 14.** Three v1 release test titles in `tests/e2e/release/optional-scope-absence.spec.ts`
  were renamed and widened since v1, so [the v1 matrix](dod-acceptance-matrix.md) quotes their
  old wording: 'no audio context, MIDI access or microphone request happens across every current
  interaction', 'no request leaves the page origin, and none is XHR, fetch, WebSocket or SSE' and
  'no playback or scoring control is ever rendered'. Chromium only is a support statement, as in
  v1 ([browser-and-offline-limits.md](browser-and-offline-limits.md#supported-browsers)); the
  tests run in Chromium only.
- **Item 15's main-thread budget** has no atom of its own; it is a hand check.
- **Item 21's re-ask after a browser drop** is covered by unit tests only. The test harness's fake
  wake lock cannot drop a lock end to end.
- **Item 5's listening test** (whether the backing sounds right) was settled by the product owner
  on 2026-10-05 (spec D185).
