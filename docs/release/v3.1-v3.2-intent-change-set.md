## A. CONTRACT 2.0 → 3.0 (MAJOR): the STABLE guarantees v3.1 and v3.2 change

**Applied 2026-10-08** (the commit `ATD: apply D246, contract 3.0 and vision 0.8 for v3.1 and v3.2`;
D246 itself was recorded in 50cf38e). The product owner explicitly confirmed A1 to A17 as worded
here on 2026-10-08 (spec D246). A1 to A16 were applied exactly as written: the fifteen atoms of A2
to A16 stay STABLE at their new versions, and `rule_mutation_profile_flip_keeps_controls` left the
contract and went back to REVIEW 0.2, tagged `changes-in-v3.1`. A17 took the CONTRACT to 3.0. Each
atom's notes record the confirmation and its date.

The confirmation asked for was: "I confirm the contract changes A1 to A16 as worded in the
v3.1 and v3.2 change set. Bump the contract to 3.0."

Every atom below is STABLE, BUSINESS-layer and listed on the CONTRACT (checked 2026-10-08). The
approach is the one taken for v3.0: each proposed wording holds for the code running now and for
the code v3.1 and v3.2 will add. A clause about Jam or presets says what holds once they exist, and
holds trivially until then. So the whole change can be applied as soon as it is confirmed, and
must be applied before the first change that breaks an old guarantee merges (the figure step
replacing the profile flip, in v3.1). Every atom except A1 stays STABLE.

Sections not named in an item are unchanged.

### A1. `rule_mutation_profile_flip_keeps_controls` 0.1: removed from the contract

- Current guarantee: "a mutation of the musical profile flips it from one to the other. The flip
  changes the profile identity only: every profile-controlled value in effect stays exactly as it
  was, and the profile is marked customized".
- Proposed: the atom leaves the CONTRACT's list. Since a STABLE BUSINESS rule is on the contract
  surface by default, it goes back to REVIEW (version 0.2, text unchanged, tagged
  `changes-in-v3.1`), because it still describes the running code and keeps its code and test
  links. It is deleted in the v3.1 change that replaces the flip with the figure step; its links
  then move to `rule_vary_settings_figure_step`, and `module_settings_mutation` loses it as a
  parent.
- Reason: v3.1 makes the figures visible settings, so a Neutral ↔ Jazz flip no longer means
  anything; Vary settings moves one figure one level instead (B8.1).

### A2. `rule_mutation_marks_profile_customized` 0.2 → 0.3

- human_name: "Mutating a Profile-Controlled Value Marks the Profile Customized" → "Mutating a
  Value the Selection Holds Marks It Customized".
- INTENT: "Keep the profile's customized mark truthful when a mutation changes a value the profile
  controls." → "Keep the selection's customized mark truthful when a mutation changes a value the
  selected musical profile or preset holds."
- LOGIC, current: "A mutation of a value the selected musical profile controls (harmonic motion,
  note density, rhythmic variety, syncopation, silence density, contour or register) marks the
  profile customized, exactly as a manual edit of that value does. The profile identity stays the
  same. Like the mutation itself, the mark lasts only for the session: when the session ends, the
  customized marking returns to what it was before the session started."
- LOGIC, proposed: "A mutation of a value the current selection holds (the selected musical
  profile, or from v3.1 the selected preset) marks the selection customized, exactly as a manual
  edit of that value does: shown as the profile's customized mark, or from v3.1 as Custom based on
  that preset. Which profile or preset is selected stays the same. The key and the mode are never
  values a selection holds, so their mutations never mark it. Like the mutation itself, the mark
  lasts only for the session: when the session ends, the customized marking returns to what it was
  before the session started."
- TECHNICAL INTERFACE: "A mutation of a value the selection holds leaves the selected profile or
  preset as it is and marks the selection customized."
- EXPECTATION, proposed: "- After a mutation of a value the selection holds, the selected profile
  or preset is unchanged and the selection is marked customized. - A mutation of a setting the
  selection does not hold, the key and the mode included, leaves the customized mark as it was. -
  After the session ends, the customized marking is what it was before the session started."
- Guarantee changed: the seven named settings are no longer the whole list. A musical profile holds
  those seven; from v3.1 a preset holds ten controls and seven figure levels, so a mutation of
  Tension, Leapiness, Arpeggio chaos or a figure level, guaranteed until now to leave the mark
  alone, marks Custom (B11). Which values each selection holds is stated by the profile and preset
  atoms.

### A5. `rule_optional_midi_privacy` 0.3 → 0.4

- LOGIC, current: "MIDI input stays private by construction, not by policy. Played notes are never
  sent in any network request, and no export other than the played-notes export ever carries them.
  They are written to browser storage only with the session they belong to, and only while the
  player has opted in to keeping them; without that opt-in they exist only in memory, for the
  current session and its review. The only way a played note ever leaves the player's machine is
  the played-notes export action, which the player explicitly triggers."
- LOGIC, proposed: the current text, then: "One thing derived from played notes is not played
  notes: the doodle a player plays to start a Jam, once the app has quantized it (its notes snapped
  to the nearest sixteenth note and reduced to one melodic line), is a generation input the player
  gave on purpose. That quantized doodle is never sent either, but it travels with the music it
  generated: it is stored with its kept session without the opt-in, carried by the generated-notes
  export (MusicXML and MIDI), and printed in the phrase replay key on the browser's console. The
  doodle's raw notes, exactly as played, remain played notes under every rule above."
- TECHNICAL INTERFACE, proposed: "No network path carries played notes or a quantized doodle; the
  only storage path for played notes is their kept session, used only after the player's opt-in;
  the played-notes export is a local file download the player triggers. A quantized doodle is
  stored with its kept session and written into the generated-notes export and the replay key's
  console line."
- EXPECTATION, proposed: "Under a network and storage spy across a full session, its review and
  every export, no played note and no quantized doodle is sent over the network; without the
  player's opt-in to keeping them, no played note is written to storage, though a Jam's quantized
  doodle may be; played notes leave the device only in a played-notes export file the player
  triggered, and a Jam's quantized doodle only in a generated-notes export file the player
  triggered."
- Guarantee changed: what reaches storage and the generated-notes export without the opt-in now
  includes the quantized doodle (C5.14, C13). Played notes themselves keep every guarantee, and
  nothing is ever sent.

## B. One bump or two

**Applied 2026-10-08: one MAJOR bump for both** (spec D246).

**Recommended: one MAJOR bump, 2.0 → 3.0, for v3.1 and v3.2 together**, applied as soon as the
owner confirms part A, and before the first v3.1 change that breaks an old guarantee merges.

- Every proposed wording holds for the running code, for v3.1 and for v3.2: the Jam clauses hold
  trivially until Jam exists, so nothing is promised early and nothing is given up early.
- The owner reviews and confirms one set of wording once, as both Part B and Part C ask, and the
  record satisfies both definitions of done (B14 item 23 and C16 item 41).
- Two bumps (3.0 when v3.1 is built, 4.0 when v3.2 is built) would ask for a second confirmation
  later and leave v3.2's wording, confirmed now, unapplied for a long time.
- The risk of one bump: if v3.2's design changes before it is built, the Jam clauses must be

**Words used below.**

- **Preset:** a saved set of generation settings (ten controls and seven figure levels) with a
  name. Eight are built in (Neutral, Jazz, Gentle, Speed drill, Reel, Bebop, Pop song, Modal
  (Dorian)); the player can save their own, called **player presets**.
- **Figure level:** how often the generator uses one embellishment figure (a note that decorates a
  chord note, such as a passing tone): Off, As today, Favored or Strongly favored. There are seven
  figures, so seven levels.
- **The selection:** what the preset box shows: a preset, or **Custom**. Custom means the settings
  were changed since a preset was chosen; it names the preset it is **based on** ("Custom, based on
  Reel"), or none.
- **Key and mode restriction:** the keys and modes a preset is meant for, such as "Mixolydian or
  Dorian, any key" for Reel. Most presets allow any key and mode.
- **Preset label:** what a kept session records about the selection at its start: the preset's
  name, or "Custom, based on …", kept as it was then.
- **Data version:** the number of the layout the app's data has on the device. When a new version
  of the app changes the layout, it carries the old data over to the new layout when it opens.

Kinds of change: **weakens** (the player gets less than the old promise said), **extends** (the
old promise holds and covers more), **shape** (a stored layout the owner put on the contract
changes; no promise to the player is weakened), **rewords** (same promise, other words).
