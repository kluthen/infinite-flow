# Generator Architecture

Status: v1.1 — Steps 2-9 are implemented, and v2's generator continuation (the carry-in, described in Delivered Generator Continuation below) is delivered: event/deterministic foundations, declarative profile/register data, typed controls/outer intent/session coordination, an immutable structural harmony candidate-domain seam, the rhythm and phrase-structure planner (Step 6), the pitch planner/validation together with generation orchestration and independent whole-result validation (Step 7), the pure written-notation transformation with VexFlow engraving (Step 8; its staff layout planner has since been replaced by v2's, described in Delivered Notation Boundary below), and the responsive, accessible phrase workspace (Step 9): a root-composed session, Web Worker generation behind a typed protocol, a seed-independent canonical rhythm-domain memo, the unsupported-rhythm-settings block, and production Tailwind 4 styles.

Amended for the v1.0 gate (2026-09-26): D56–D60, D73. The instrument profile carries its concert-to-written transposition and the key is chosen in written pitch (no separate display convention); rhythmic variety is added and the Mixed note density is retired; musical-profile behavior is gated by named capabilities. The master spec (draft v2.0) is authoritative; where this document describes delivered Step 2-9 code, it describes the pre-gate implementation unless a sentence says otherwise.

## Architectural Intent

The musical generator must be highly decoupled so that a new harmonic language, rhythm strategy, phrase model, backing generator, or adaptation method can be introduced without rewriting unrelated musical logic or the user interface.

The four-measure generator is the first consumer of these seams. The later MIDI-seeded, rolling generator must reuse the same seams rather than becoming a separate engine.

## Generator Profiles

The default profile is style-neutral. It must not import jazz-specific assumptions into the shared generator contracts. Its initial grammar uses a selected major, minor, or modal scale; mostly diatonic chord movement; chord tones and scale passing tones; and tension from non-chord scale tones, rhythm, contour, and silence. It excludes substitutions, altered dominants, and chromatic enclosures.

An optional jazz-oriented profile is included early to validate that a different harmonic and melodic vocabulary can be selected without coupling generators to a single style.

Its initial extension permits chromatic approaches and enclosures around target tones. It does not yet permit altered dominants or harmonic substitutions. The jazz profile declares this through a named capability, _chromatic approach and enclosure figures allowed_; planners and validators check declared capabilities, never a profile's name, so a later profile (or character preset) can combine capabilities without new name checks.

(proposed) A profile supplies theory vocabulary and planner policies: allowed scales and chord qualities, harmonic motion, tension devices, rhythm tendencies, contour preferences, and voicing or backing conventions. It does not own UI controls, browser APIs, audio scheduling, or persistent session state.

For the first deliverable, the implemented control-mapping boundary validates closed catalogs before planner consumption: 60-240 BPM in ten-BPM increments, twelve pitch classes (selected in the instrument profile's written pitch and converted to concert pitch at intent construction), Major/Minor and seven named modes, and the documented musical controls. Its literal first-load state is 90 BPM, C Ionian, Neutral, Lift, Shaped, B-flat tenor, and Predictable. Direct chord-progression selection is deferred.

The same seam maps contour, register, leapiness, and arpeggio chaos controls into pitch-planner policy. The pitch planner must use these values as constraints or weighted preferences, not as UI concepts. Arpeggio chaos controls the ordering and interval contrast of eligible chord tones; it does not override profile pitch vocabulary or resolution rules.

The first request contract fixes meter at 4/4 and carries a user-selected, stable BPM. A rhythm policy supplies the dominant subdivision (quarters, eighths, or sixteenths), a rhythmic-variety level (Strict, Slightly varied, or Heavily varied) setting how often shorter and longer values appear, syncopation (straight through active displacement), and rest behavior (sparse through breath-heavy); meter changes, deliberate tempo changes, and pulse-feel controls remain later extensions.

Notation consumes the stable generated event model. Standard staff rendering is required for the first deliverable and becomes a rolling-window renderer later; it must not cause generator behavior or alter the underlying concert-pitch event data. A selected declarative instrument profile supplies an inclusive active concert range and a whole-phrase register window: C MIDI keyboard `48-72`, B-flat tenor saxophone `46-70`, or E-flat alto saxophone `51-75`, with the adopted contained overlapping Low, Middle, and High windows. `Varying` deterministically resolves one feasible window before planning and never changes it mid-phrase. The same instrument profile supplies its concert-to-written transposition as open data (integer chromatic semitones and diatonic letter steps): C MIDI keyboard `+0/+0`, B-flat tenor `+14 semitones/+8 diatonic steps`, and E-flat alto `+9/+5`. There is no separate display convention. Transposition is used in exactly two places: intent construction converts the player's written tonal center to concert pitch, and notation writes the concert timeline in treble G2 clef in the instrument's written pitch. No planner reads it, and notation never regenerates material, changes the selected profile/range/window, or mutates concert-pitch events. Adding an instrument profile is one declarative entry, with no new type, enumeration member, or UI branch.

## Delivered Outer Request Boundary

`GenerationIntent` is now the immutable, serializable outer boundary. It owns request identity/seed, fixed four measures/4/4, normalized controls, selected musical-profile identity/custom state, selected Step 3 declarative instrument profile, and outer `RegisterIntent`. `Varying` deliberately remains unresolved at this boundary. Step 7 alone will project fixed choices or an eligible Varying candidate into the unchanged resolved `GenerationRequest`; no range/window algorithm is duplicated in Step 4.

Neutral and Jazz are frozen replacement bundles, not mutable configurations: Neutral is Static/Quarter/Slightly varied/Straight/Sparse/Arch/Middle and Jazz is Gentle diatonic/Eighth/Slightly varied/Occasional offbeats/Conversational/Wandering/Varying (rhythmic variety joins the bundle at the v1.0 gate). Reselecting replaces all seven values. Editing one produces custom values while retaining the selected profile grammar identity; edits outside that set do not falsely change profile state.

The root-created `createGenerationSession` factory is the application coordination boundary for this step. It has no singleton, storage, component, or browser-randomness dependency. It exposes readonly state and explicit actions, permits exactly one generation or notation operation, suppresses configuration edits while either runs, retains a prior valid result after later failures, and builds both regeneration and generation retry from current controls/profile with fresh injected identity/seed (retry does not replay the failed intent; user decision, 2026-09-25). Its injected pre-engraving notation seam engraves a result, retains the phrase after failure, and retries the same result without touching generation providers. (Before the v1.0 gate it also committed a separately selected display mode; that selection is removed.) Theme remains immediate and presentation settings stay separate from generation data. Step 9 (below) is what actually wires this factory into one root-composed session, a Worker-backed generation seam, and the mounted workspace component tree.

## Delivered Phrase Workspace (Step 9)

The Step 9 workspace is the one production consumer of `createGenerationSession`. `App.vue` builds a single root `WorkspaceSession` for the browser tab's lifetime through `createWorkspaceSession`, which supplies the session's injected seams: a cryptographic per-generation seed provider, a monotonic request-id provider, a `generate` seam backed by one long-lived generation Web Worker behind a typed protocol with two inbound messages (a correlated `generate` answered by exactly one response, and an uncorrelated `prewarm` that is never answered), a `notate` seam driven by a dedicated notation coordinator around one mounted `PhraseScore` instance, and the profile-switch policy adapter. The component tree (`WorkspaceShell`, `WorkspaceHeader`, `ScorePanel`, `ControlPanel` and its four control groups, `OrientationNotice`) is props-in/events-out around that one session, production styling is Tailwind 4 (`src/styles/theme.css`/`components.css`), and a seed-independent canonical rhythm-domain memo lets the worker reuse an already-materialized rhythm domain across repeated generations against the same rhythm setting. A `prewarm` message makes the Worker build the current rhythm setting's domain into that memo in the background, in slices of about 8 ms (one gesture unit each) that yield through a private `MessageChannel`, so a `generate` is served within about one slice; the page posts one through an injectable prewarm policy (on in production, `?prewarm=off` being the latency-measurement switch) when the Worker starts and whenever the width-resolved rhythm setting changes (`generation-worker-runtime.ts`, `src/components/workspace/prewarm-policy.ts`, `src/composables/generation-session-prewarm.ts`). A domain-owned constant blocks Generate/Regenerate for the six rhythm settings that have no legal four-bar plan under any tension arc, without ever locking the controls themselves. See [docs/phrase-workspace.md](../docs/phrase-workspace.md) for the full component tree, session wiring, state map, Worker protocol, rhythm-domain memo, unsupported-rhythm-settings block, and accessibility behavior, and [docs/generation-latency.md](../docs/generation-latency.md) for the measured cold/warm latency and the proposed budget.

## Delivered Harmony Candidate Domain

`makeHarmonyCandidateDomain` is the Step 5 pure structural planner boundary. It validates and projects only tonal center, collection, harmonic motion, tension arc, and musical-profile identity; it returns either an immutable `HarmonyCandidateDomain` or the typed `no_legal_harmony_plan` result. The success shape contains exact collection pitch classes and all seven derived root-position diatonic triads, then a complete canonical candidate list. Every candidate has a stable serialized identity, contiguous zero-based index, merged quarter-boundary chord events with preserved per-bar roles, an open endpoint class, and an abstract rhythm-independent tension requirement.

This seam has no seed or random-stream dependency and does not receive rhythm/onsets, register/instrument profile, contour, pitch feasibility, ranking, selection, orchestration, Vue, browser, storage, or session state. It must return an identical domain for Neutral and Jazz under equal harmony controls. Major/Minor select tonal templates while named Ionian/Aeolian remain modal; expansion follows Harmony Planner Policy document order, ascending degree alternatives, and unsplit-before-split variants. Step 7 may bind/rank candidates but cannot mutate their structure, identity, or index.

## Delivered Notation Boundary

Notation is a pure consumer of a successful generation outcome. `notationInputFromOutcome` reads only the result's concert timeline, the intent's tonal context (tonal center and collection), and the selected harmony candidate recorded in `GenerationOutcome.provenance.harmony`; it never reaches into planner internals and never changes `GenerationRequest` or `GenerationResult`. `transformToWrittenPhrase(input, mode)` then produces a deep-frozen `WrittenPhrase` for Concert, B-flat tenor, or E-flat alto display. At the v1.0 gate the closed `mode` gives way to the selected instrument profile's open transposition data, and the written key is the player's selection. It spells the key, notes, chord roots, and slash bass with one consistent enharmonic rule (fewest accidentals, sharps on a tie). It also segments durations into notated values with ties and beam groups, and derives displayed accidentals per measure. Transforming never regenerates anything or mutates the source events.

Engraving is a separate browser adapter. It is the only code allowed to import the pinned VexFlow library. The staff layout is decided by a pure planner (`planSystemLayout` in `src/notation/notation-layout-policy.ts`) that never touches VexFlow or the page, so its arithmetic is tested on its own. The viewport's width alone picks the layout, at `bp-tablet-landscape` (`64rem`), and the planner never tries one layout before the other. From `64rem` up, one staff system holds all four measures. Below it (the landscape phone layout), every phrase is split, at idle as in a session: measures 1–2 on the top system, measures 3–4 on the one below. In either layout every measure gets the same width, the width the phrase's widest measure needs, so the measures read as equal and the two systems' measure columns line up.

The whole phrase is engraved at one uniform scale: the largest that fits the container's width and, below `64rem`, the height budget too, never below the legibility floor of 5 px per staff space (a staff space is the gap between two neighbouring staff lines) and never above 12 px. `PhraseScore.vue` reads that height budget from `staff-frame`'s computed `max-block-size`, which the stylesheet builds from the small viewport height (`100svh`, the height with the browser's toolbars showing), minus the frame's padding and border. It engraves again only when the phrase, the container width, the height budget or the layout changes, so a browser toolbar showing or hiding never redraws the staff. The staff area always reserves two system positions, in every state, with or without a phrase: both have one block size, 16 staff spaces at the largest scale the viewport allows (from `64rem` up, the 12 px maximum; below it, the largest that fits the height budget), set from the viewport and never from a phrase or an instrument profile. Within each position the staff is placed from the selected profile's written range (higher for the C MIDI keyboard, which reaches low; lower for the saxophones, which reach high), never from a phrase's notes. Each position that shows notes is its own `staff-content` unit holding its own engraving, one SVG per system.

When a phrase cannot be drawn at the legibility floor, the planner returns one of two distinct typed failures, and the adapter surfaces each as its own `NotationError` code (`isStaffLayoutFailure` tells them apart from the failures a retry can cure). It never scrolls, clips, splits further, or shrinks without bound instead. "No room for the staff" (`notation_no_room`) is about the window, whatever the phrase: it is too narrow for the clef, key signature and time signature plus every measure at its minimum width, or, below `64rem`, too short for both system positions; the planner checks it first. "Notes too wide" (`notation_notes_too_wide`) is about this phrase: the window has room, but this phrase's measures need more width. Neither failure reaches into the generator. What to do about each one is the workspace's decision: the v2 master spec answers "notes too wide" at idle with fresh generation requests and "no room" with a notice that the staff needs more room; until the workspace does that, it shows both as the retryable notation error. A spoken-English score description accompanies each successful engraving, attached to the top system; the split layout's bottom system is hidden from assistive technology so the phrase is announced once. docs/notation-engraving.md records the pinned library boundary, the bundled font assets and their licenses, the domain-to-engraving mapping, the sizing and failure policy, the accessible representation, and the upgrade procedure.

## Delivered Generator Continuation (v2)

In a v2 session, phrases play one after another, and each phrase after the first is generated from a small handoff from the phrase before it, the **carry-in**. It is the only thing that crosses a join between two phrases, and it holds exactly four items:

1. the last sounding concert pitch of the phrase before, with its leap state there: the interval that arrived at it (none for a phrase's single note with no pitch carried into it) and whether it still owes the recovery of a large leap, and in which direction;
2. the register window that phrase was resolved to;
3. its final chord (the triad and its harmonic role) and the endpoint class of the harmony candidate that ends on it;
4. the phrase number: that phrase's position in its session, counted from 1.

Tempo, seeds, settings and every other fact of the phrase stay behind; tempo never enters generation at all.

**Where it lives.** `carryIn` is an optional field of both `GenerationIntent` and the resolved `GenerationRequest`, and the request carries the intent's carry-in unchanged. Without carry-in the field is absent, not empty, so a request serializes exactly as in v1 and the output for a given request and seed is byte-identical to v1.

**Validated three times.** Every refusal is a typed error (`CarryInError`, or `GenerationRequestError` for a request's carry-in).

- _By its constructor._ `makeCarryIn` builds every carry-in, deep-frozen. It refuses a pitch outside the carried window; an arriving interval that is not a whole number of half steps within an octave; an owed recovery whose arriving interval is not at least a skip in the owed direction; a tense carried pitch (outside the carried chord) not reached by a step; a malformed chord, role or endpoint class; and a phrase number that is not a positive whole number.
- _Against the receiving intent._ `makeGenerationIntent` checks that the intent can honour it (`assertCarryInFitsIntent`): the carried window must be one the register choice resolves to (the chosen register's window, or for Varying any of its windows); the carried chord and endpoint class must be one these harmony settings end a phrase on; and anything owed must be a debt a phrase may end with that the next phrase's first note can settle inside the window. `makeGenerationRequest` also refuses a carry-in whose window is not the request's resolved window.
- _At the worker boundary._ A structured clone loses freezing and can be corrupted, so `parseCarryIn` rebuilds the carry-in field by field, refusing any missing, extra or malformed field at every level and never filling in a default, then passes it through `makeCarryIn`. The intent is rebuilt through `makeGenerationIntent`, so the checks against the intent run again, and `parseGenerationRequest` does the same for a request's carry-in.

**Derived from a generated phrase.** `deriveCarryIn` reads only one successful phrase's own outcome (its timeline, resolved request, and selected harmony and rhythm), the leapiness it was generated with, and the phrase number it is given. It replays the phrase's sounding notes through the same leap-state reducer the pitch planner uses, starting from the phrase's own carry-in when it had one, so the carried leap state is exactly the state after the phrase's last sounding note. When a phrase sounds only one note, its arriving interval is measured from the pitch carried into it.

**Resolution.** An intent with a carry-in resolves to exactly one core request, for the carried register window. Varying is therefore never re-resolved: the window resolved for a session's phrase 1 is reused by every later phrase. A pitch search that fails in that window is reported as `no_legal_pitch_plan`, as for a fixed register. Without carry-in, resolution is unchanged: one request for a fixed register, one per window for Varying.

**Harmony.** The structural harmony candidate domain is unchanged by a join. The carried chord must be one the settings end a phrase on: the degree-5 open arrival, or the tonic (degree 1) that static and modal harmony end on. Every template opens on the collection's tonic, so the join is always a move from degree 5 to degree 1 (V to I; in Minor, v to i) or a restatement of the tonic. Orchestration keeps, in domain order, the candidates that may follow the carried chord (`candidatesFollowingCarriedHarmony`) and ranks them with the seed as before.

**Pitch planner.** The search is seeded from the carried motion state (`carriedMotionState`): the carried pitch is the note sounding before beat 1. So the new phrase's first interval meets the same interval cap as two consecutive notes inside one phrase and counts in the phrase's leap budget; a same-direction chain of skips or leaps arriving at the carried pitch stays open; an owed large-leap recovery falls due on the first note; and a tense carried pitch must be resolved by the first note, one scale step (1-2 half steps, both notes in the collection) onto a tone of the chord sounding there. The notes before the join are given a position no note of the new phrase has, so a chain spanning the join is never taken for a chord-tone run. Tension figures stay inside one phrase: the carried pitch never prepares a non-chord tone of the new phrase.

**What a phrase may end owing.** `phraseEndingDebtAllowance` is the single place this is decided, and the pitch planner and the validators both read it. Without carry-in (the Idle phrase that becomes phrase 1, or the failure ladder's standalone phrase), a phrase owes nothing at its end, as v1 requires. With carry-in, a phrase may end owing a large leap's recovery or a tense note's resolution, but only what the next phrase can settle. The next phrase opens over the tonic triad, so an owed recovery must be able to land on a tonic-triad tone 1-4 half steps back against the leap, and a tense final note (a scale tone outside its chord, reached by a step) must be able to move one scale step onto a tonic-triad tone, in both cases inside the register window the next phrase inherits. These two checks (`owedRecoveryCanSettle`, `tenseNoteCanSettle`) are pure pitch arithmetic kept beside the allowance, so the planner and the validator share them without the validator reading planner code.

**Independent validation.** The independent result validator judges the join and the endings the same way, rebuilt only from the carry-in, the request and the phrase's own sounding notes: the carried pitch is the note before the first attack for the interval, chain and recovery rules; a tense carried pitch the first attack does not resolve fails (`carried_tension_unresolved`); and the endings read the same allowance and settle checks. It also checks that the intent and the request hold the same carry-in (`carry_in_mismatch`), that the resolved window is the carried one (`carry_in_register_window_mismatch`), and that the phrase's harmony follows the carried chord, opening on the tonic (`harmony_join_invalid`).

**Only forward.** Carry-in flows forward only. A phrase reads the carry-in of the phrase before it; `deriveCarryIn` reads a finished phrase and never changes it, and nothing a later phrase does revises an earlier one. Letting a later phrase edit an earlier one is deferred to v3.

**Not part of this delivery.** Which carry-in each session phrase is generated with (none for phrase 1, the same one for a retry, none for the failure ladder's standalone phrase) and the phrase numbering belong to the session, which does not use the carry-in yet. v2.1's setting changes at a phrase boundary are not handled either: the v2 master spec has a key or collection change drop the harmonic part of carry-in while its pitch part still applies, and a register change re-resolve Varying, but the delivered carry-in has no partial form, and one that does not fit the receiving intent's settings is refused. v2.0 locks every generation setting for the whole session, so this does not arise before v2.1.

## Proposed Generator Contract

(proposed) A resolved planner request provides only normalized musical context: meter, requested measure count, tonal/harmonic context, a selected instrument-profile identity with its explicit active range and one resolved register window, the carry-in from the phrase before when the phrase continues a session (see Delivered Generator Continuation above), control values, a deterministic random seed, and an explicit generator-profile identifier. Tempo is never one of them: it stays in the outer intent's controls for the transport only, and the same request and seed give the same phrase at every tempo.

(proposed) A generation result returns a timeline of measures, note events, rests, chord events, and explanations or labels suitable for display. It does not render notation, schedule audio, read MIDI, or mutate application state.

This boundary makes a generated four-measure proposal reproducible from the same input, and lets the UI, playback layer, and later evaluator consume one stable event model.

## Candidate Musical Seams

- **Control mapping:** translates user-facing knobs into a normalized musical policy. A knob does not call a specific generator directly.
- **Harmony planner:** delivered as an ordered immutable structural candidate domain; it does not choose a chord/tension plan or bind rhythm.
- **Rhythm planner:** allocates onset opportunities, subdivisions, syncopation, and rests independently of exact pitches.
- **Pitch planner:** assigns pitches to the rhythm plan from harmonic constraints, contour, register, and permitted outside-chord behavior.
- **Phrase transformer:** optionally derives material from a seed phrase. It is absent in the first deliverable and is added for MIDI continuation without replacing harmony, rhythm, or pitch planning.
- **Backing arranger:** optionally derives BPM-aligned accompaniment events from the harmony and rhythm plans. It remains optional and must not be required to create the note proposal or play back the generated lead line.
- **Evaluator:** compares incoming MIDI events with an already generated proposal. It does not influence generation unless a later adaptation policy explicitly requests it.

Each seam consumes and produces explicit, serializable data. It should not reach into browser APIs, controls, audio state, or another seam's internal state.

MIDI integration is not part of v1 and sits outside the evaluator. When v2 adds it, it acknowledges only a played note that matches the expected note, with no mismatch hint (D52, D66 in `archive/2026-09-25-personas-and-vision/decisions-D47-D71.md`). MIDI input is read as concert pitch (D72). It never computes a score or alters generator state. The v2 design is in `versions/v2/master-spec.md` (§8–§9).

## Evolution Rules

- A new musical style is a selectable profile or a new implementation behind a stable planner contract, not conditionals scattered across UI and playback code.
- The current profile's theory vocabulary is data or policy where practical; it is not encoded into generic scheduling or notation code.
- Randomness is injected through the request seed. The same request must regenerate the same four measures, allowing a phrase to be inspected and tested.
- A user-triggered regeneration keeps the control policy but creates a new seed. The generated result retains that seed for exact reproduction.
- Generator stages may attach musical annotations such as tension role, chord degree, or source transformation. Consumers may use these annotations, but must not infer hidden generator state.
- The application orchestration layer chooses and connects planner implementations. Individual planners do not select, instantiate, or import one another.

The notation representation is resolved by Step 8: see Delivered Notation Boundary above and docs/notation-engraving.md.
